## ✅ ИСПРАВЛЕНО — 1. Синхронные HTTP-вызовы блокируют event loop

**Файлы:** `app/services/maxbot.py:6`, `app/services/bitrix.py:15`

`httpx.post` вызывается синхронно внутри async FastAPI-хендлеров. При медленном ответе edna или Bitrix (300–500ms) event loop блокируется, и реальная пропускная способность составит 2–3 сообщения в секунду вместо требуемых 50.

**Решение:** заменить синхронный `httpx.post` на `async with httpx.AsyncClient` с `await`.

## ✅ ИСПРАВЛЕНО (не протестировано) — 2. Ошибка отправки в MAX Bot не сообщается оператору

**Файлы:** `app/services/delivery_worker.py`, `app/services/bitrix.py`

При сбое отправки сообщения в edna ошибка только логировалась. Оператор не видел, что сообщение не доставлено. Нарушало требование PRD раздел 4.3.

**Важная поправка по API:** метода `imconnector.send.status.undelivered` (как предполагалось изначально) в Bitrix REST **не существует**. Connector-API Открытых линий для исходящих сообщений даёт только *положительные* статусы: `imconnector.send.status.delivery` (доставлено) и `...status.reading` (прочитано). Нативной пометки «не доставлено» под сообщением оператора Bitrix приложениям не предоставляет.

**Что сделано (обходной путь):** при окончательном провале доставки исходящего сообщения в edna (статус задачи `dead` после исчерпания повторов / постоянной ошибки, либо `failed` при истёкшем файл-кеше) воркер вставляет в тот же диалог Открытой линии видимую строку-предупреждение через `imconnector.send.messages`:
- текст «⚠️ Сообщение не доставлено клиенту в MAX. Попробуйте отправить ещё раз.» (для файлов — «Файл не доставлен…»);
- привязка к существующему диалогу по `chat.id` (= `max_id` клиента) и `LINE` (= `line_id` из задачи, фолбэк `portal.open_line_id`);
- `disable_crm: Y` — не засоряет CRM-трекер;
- уведомление best-effort: его собственный сбой не ломает воркер и не влияет на статус задачи.

Новый хелпер `send_undelivered_notice()` в `bitrix.py`; вызов из `_notify_outgoing_undelivered()` в `delivery_worker.py` в обеих ветках окончательного провала (только для задач `send_to_edna`). Транзиентные повторы (статус снова `pending`) уведомление НЕ шлют — только окончательный отказ.

**Ограничение (принято осознанно):** предупреждение выглядит как отдельная строка в переписке, а не как пометка под конкретным сообщением (ограничение Bitrix API). Ловятся только сбои, о которых edna сообщает синхронно (ошибка в ответе); если edna примет сообщение и доставка отвалится асинхронно на её стороне — мы об этом не узнаем.

**Как протестировать (тумблер `EDNA_FORCE_FAIL`):** нужно намеренно вызвать постоянную ошибку отправки в edna. Подмена ключа через #7 не подходит — там новый ключ валидируется в edna перед сохранением, неверный ключ форма не примет. Поэтому добавлен тест-тумблер (`app/config.py` → `edna_force_fail`, по умолчанию выключен):

1. В панели Render задать переменную окружения `EDNA_FORCE_FAIL=1` (сервис перезапустится).
2. Оператор пишет любое сообщение в подключённый диалог Открытой линии.
3. Отправка в edna сразу падает с постоянной ошибкой → задача уходит в `dead` (без 45 мин повторов) → в переписке должна появиться строка «⚠️ Сообщение не доставлено клиенту в MAX…».
4. Убрать переменную `EDNA_FORCE_FAIL` (или поставить `0`) → отправка снова работает штатно.

Тумблер влияет только на исходящие (`_execute_outgoing`), затрагивает все каналы на время теста — поэтому включать его на короткое окно. Несколько строк тест-кода можно оставить (выключен по умолчанию) или убрать после проверки.

## ✅ ИСПРАВЛЕНО — 3. SQLite по умолчанию — риск при деплое с несколькими workers

**Файл:** `app/config.py:4`

`database_url` по умолчанию указывает на SQLite. SQLite не поддерживает одновременные записи от нескольких Uvicorn workers. Если при деплое не задать `DATABASE_URL`, приложение молча запустится на SQLite и будет давать ошибки при нагрузке.

**Решение:** либо сделать `DATABASE_URL` обязательной переменной (без дефолта), либо явно документировать риск и выводить предупреждение при старте если используется SQLite.

## ✅ ИСПРАВЛЕНО — 4. Манифесты MAX Bot не описывают файловый API

**Файлы:** `MAX Bot Incoming - LLM Manifest.md`, `MAX Bot send message - LLM Manifest.md`

Входящий манифест показывает `attachment: null` в примере — вложения технически существуют, но не задокументированы. Исходящий манифест описывает только `content.type: TEXT`, эндпоинта для отправки файлов нет. Без обновлённых манифестов нельзя планировать реализацию файлового обмена.

**Решение:** получить от edna обновлённые манифесты с описанием файлового API (входящий вебхук с вложением и исходящий запрос с файлом).

## 7. Нет возможности изменить API-ключ существующего канала

**Файл:** `app/routers/api.py`, фронтенд настроек

При подключении канала API-ключ сохраняется один раз. Если ключ изменился (перевыпуск, компрометация), оператор не может обновить его — только отключить канал и создать новый, теряя историю сообщений и связку с открытой линией.

**Решение:** добавить эндпоинт `PATCH /api/channels/{channel_id}` и форму редактирования в настройках. В `ChannelResponse` api_key намеренно не возвращается — отображать в форме только последние 4 символа (`****...XXXX`).

## ✅ ИСПРАВЛЕНО — 9. Кнопка «Скопировать» для webhook URL не работает

**Файл:** `app/routers/settings_page.py` (функция `copyWebhook`)

Кнопка «Скопировать» под URL для приёма входящих сообщений из MAX Bot не копирует URL в буфер обмена. Скорее всего причина — `navigator.clipboard.writeText` не работает в iframe без разрешения `clipboard-write`, а страница настроек открывается внутри iframe Bitrix24.

## ✅ ИСПРАВЛЕНО (задеплоено, проверить на портале) — 16. UI-диалоги переведены на внутренние модалки

**Решение:** собственное модальное окно в стиле edna (без JS Bootstrap, чистый JS):
- `confirm()` → `showConfirm(message, onOk)` — две кнопки (OK / Отмена)
- `alert()` → `showNotice(message)` — одна кнопка (Понятно)
- Закрытие: кнопки, клик по затемнённому фону, клавиша Escape

### ✅ ИСПРАВЛЕНО — SEC-4. URL файлов публичны и не имеют TTL

**Файлы:** `app/routers/files.py`, `app/services/file_cache.py`, `app/routers/handler.py`

**Что сделано:** URL файлов теперь защищён HMAC-подписью с временным ограничением.

Формат URL: `/file/{uuid}.{ext}?token=HMAC-SHA256(secret_key, "{uuid}.{ext}:{expires}")&expires={unix_timestamp}`

- Запрос без `token` и `expires` → `403 Forbidden`
- Несовпадение подписи или истёкшее время → `403 Forbidden`
- Ключ подписи — `SECRET_KEY` из переменных окружения (тот же, что для шифрования БД)
- TTL токена — **10 минут** (совпадает с TTL кеша)

**Техническое ограничение:** файлы хранятся только в памяти сервера в течение 10 минут с момента отправки оператором. По истечении этого времени URL перестаёт работать (файл удаляется из кеша). Это приемлемо, так как MAX Bot скачивает файл за секунды и хранит его на своём сервере. Долгосрочное решение — переход на S3-совместимое хранилище (см. PROD-3).

### ✅ ИСПРАВЛЕНО — SEC-6. Нет rate limiting

### ✅ ИСПРАВЛЕНО — SEC-7. Нет строгой валидации входящих данных

**Файлы:** `app/services/sanitize.py`, `app/routers/incoming.py`, `app/routers/handler.py`

~~Payload от edna и Bitrix24 парсится «как есть», без строгих Pydantic-схем. Некорректный payload может вызвать неожиданное поведение или crash.~~

**Что сделано:**
- Защита от crash на некорректном payload: если тело — не JSON-объект (массив, строка, число), `incoming.py` возвращает `400 Bad Request`, `handler.py` — `200 OK` (чтобы Bitrix не повторял). Все вложенные объекты (`messageContent`, `subscriber`, `userInfo`, `attachment`, `location`, `auth`) проверяются на тип `dict` перед обращением — раньше нестандартный тип ронял хендлер.
- Лимиты длины: текст сообщения — **4096 символов**, имя пользователя — **255 символов** (в `sanitize.py`).

**Решение по подходу (отличие от исходного ТЗ):** вместо отклонения слишком длинных сообщений (`400`) текст **обрезается** до лимита. В нашей модели доставки `400` означает «edna не повторит запрос» — то есть длинное сообщение клиента было бы потеряно полностью. Обрезка сохраняет сообщение. Полноценные Pydantic-схемы не вводились намеренно: payload от edna имеет гибкую вложенную структуру (TEXT / LOCATION / вложения), и строгая схема с обязательными полями рисковала бы отклонять валидные сообщения на ещё не протестированной на проде очереди доставки.

**✅ Протестировано на живом сервере 2026-06-07.** Выяснилось, что **MAX сам разбивает длинные сообщения** на части перед отправкой вебхука: очень длинное сообщение пришло двумя кусками (3991 и 3983 символа), каждый меньше лимита 4096. Поэтому обрезка в обычной жизни почти не срабатывает — нормальные сообщения проходят без искажений, и это правильно.

Лимит **оставлен намеренно как подстраховка** (defense in depth): если кто-то будет слать запросы в `/incoming` напрямую, в обход MAX, лимит и проверки типов защитят сервер от гигантского/битого payload. На «доброе поведение» внешнего сервиса не полагаемся.

**Файлы:** `app/services/sanitize.py`, `app/routers/incoming.py`

~~Текст входящих сообщений от клиентов (через edna) не очищается перед передачей в Bitrix24. Если в UI Bitrix появится HTML-рендеринг, BBCode с вложенным JS/HTML — потенциальный XSS.~~

**Что сделано:**
- Реализован exponential backoff в delivery worker: расписание `[1с, 5с, 30с, 2м, 10м, 30м]`, максимум 6 попыток
- Классификация ошибок: transient (408, 429, 5xx, сетевые) → retry; permanent (4xx, RuntimeError, PaymentRequiredError) → сразу `dead`
- `FileNotFoundError` (истёкший file cache) → сразу `failed` без retry
- После 6 неудачных попыток задача получает статус `dead` с сохранением `last_error`

Коммит: `010ecf6`

### ✅ ИСПРАВЛЕНО (не протестировано) — REL-2. `/incoming` возвращает 200 только если задача сохранена

**Файл:** `app/routers/incoming.py`

~~Если отправка в Bitrix24 упала, код ловит исключение, логирует и всё равно возвращает `{"status": "ok"}`. edna считает webhook доставленным и не повторяет — сообщение теряется.~~

**Что сделано:**
- JSON parse failure → `400 Bad Request`
- Задача успешно добавлена в очередь → `200 OK`
- Ошибка при сохранении в БД → `503 Service Unavailable`
- `IntegrityError` (дубль) → `200 OK` (идемпотентно)

Коммит: `37d6026`

### ✅ ИСПРАВЛЕНО — REL-3. Нет идемпотентности — при повторном webhook создаются дубли

**Файлы:** `app/routers/incoming.py`, `app/main.py`

**Что сделано:**
- `main.py` — при старте создаётся уникальный индекс БД по `(channel_id, direction, max_message_id)` для входящих сообщений
- `incoming.py` — двухуровневая защита: сначала явная проверка по `max_message_id` до вставки (быстрый путь), затем перехват `IntegrityError` при одновременных запросах (race condition). Оба случая возвращают `200 OK` и логируют `duplicate message id=...`

**Примечание:** идемпотентность для исходящих (Bitrix → edna) не реализована — там другой механизм защиты через anti-replay в SEC-2.

---

### ✅ ИСПРАВЛЕНО (не протестировано) — REL-4. Очередь сообщений с persistence в PostgreSQL

**Файлы:** `app/models.py`, `app/services/delivery_worker.py`, `app/routers/incoming.py`, `app/routers/handler.py`, `app/main.py`

~~Внешний API (edna или Bitrix24) вызывается синхронно внутри обработчика входящего запроса. Если внешний сервис временно недоступен — сообщение теряется, нет возможности повторить.~~

**Что сделано:**
- Таблица `message_delivery_tasks`: статусы `pending → processing → sent / failed / dead`, retry_count, next_attempt_at, last_error
- Фоновый asyncio worker стартует при запуске (`@app.on_event("startup")`) — читает очередь, доставляет, обновляет статус
- `incoming.py` и `handler.py` только сохраняют задачу в БД и сразу возвращают 200 OK
- Дедупликация для входящих: двойная проверка по `max_message_id` (таблица `Message` + таблица `MessageDeliveryTask`) + уникальный индекс в БД
- `handler.py` по-прежнему всегда возвращает 200 OK — иначе Bitrix24 будет повторять запрос и создавать дубли (ADR-6)
- Файлы из Bitrix скачиваются немедленно в handler (пока SIGN не истёк), в задачу кладётся только `file_key`; worker вызывает `make_signed_url(file_key)` при отправке

Коммиты: `d2c180b` (модель + миграция), `010ecf6` (worker), `37d6026` (incoming), `8e3cdc5` (handler + startup)

## БЛОК: PRODUCTION-READINESS

Источник: `system_feedback.pdf`. Задачи для перехода от MVP к production-grade.

---

### PROD-1. Расширенная модель данных

**Файл:** `app/models.py`

Для полноценного расследования инцидентов и надёжной доставки не хватает отдельных сущностей: `delivery_tasks`, `webhook_events`, `file_objects`, `audit_logs`, `channel_secrets`, `integration_errors`.

**Решение:** спроектировать и добавить недостающие таблицы через Alembic-миграции. Добавить уникальные индексы для дедупликации. Добавить транзакции вокруг создания сообщений и delivery task.

---

### PROD-2. Observability — структурированные логи, метрики, health checks

**Файлы:** весь проект

Сейчас нет структурированных логов, correlation ID, метрик и нормальных health checks. При инциденте сложно понять что пошло не так.

**Решение:**
- Structured JSON logs с `request_id` / `correlation_id`
- Маскировка секретов в логах (см. SEC-8)
- Метрики: входящие webhook, latency, ошибки Bitrix/edna, очередь, retry, dead-letter
- `/health/live` — приложение запущено
- `/health/ready` — БД и внешние зависимости доступны
- Алерты: 5xx > 5% за минуту, spike входящих, ошибки edna API

---

### PROD-3. Хранение файлов — S3 вместо in-memory кеша

**Файл:** `app/services/file_cache.py`

In-memory кеш не подходит для production: файлы теряются при рестарте, нет масштабирования, нет lifecycle cleanup.

**Решение:** хранить файлы во внешнем S3-compatible object storage (например Cloudflare R2, Backblaze B2). Генерировать signed URL с TTL. Lifecycle policy — удалять файлы старше N часов. (Связано с SEC-4, SEC-5)

---

### PROD-4. Конфигурация окружений

**Файл:** `app/config.py`, `.env.example`

Нет разделения между local / dev / staging / production. Один набор переменных используется везде — риск случайно применить тестовые credentials в проде или наоборот.

**Решение:** задокументировать и выделить обязательные переменные для каждого окружения. Запрещать запуск production-режима без полного набора env. Staging должен иметь отдельную БД, отдельные OAuth credentials, отдельный webhook URL.

### PROD-5. CI/CD pipeline

**Решение:** GitHub Actions с шагами: lint → type check → tests → dependency audit → Docker build → migration check → deploy to staging → smoke tests. Rollback при провале smoke tests.
