# Review: замечания по коду

## ✅ ИСПРАВЛЕНО — 1. Синхронные HTTP-вызовы блокируют event loop

**Файлы:** `app/services/maxbot.py:6`, `app/services/bitrix.py:15`

`httpx.post` вызывается синхронно внутри async FastAPI-хендлеров. При медленном ответе edna или Bitrix (300–500ms) event loop блокируется, и реальная пропускная способность составит 2–3 сообщения в секунду вместо требуемых 50.

**Решение:** заменить синхронный `httpx.post` на `async with httpx.AsyncClient` с `await`.

---

## 2. Ошибка отправки в MAX Bot не сообщается оператору

**Файл:** `app/routers/handler.py:202`

При сбое отправки сообщения в edna ошибка только логируется. В Bitrix24 не отправляется `imconnector.send.status.undelivered`, поэтому оператор не видит, что сообщение не доставлено. Нарушает требование PRD раздел 4.3.

**Решение:** при ошибке отправки в edna вызывать `imconnector.send.status.undelivered` с идентификаторами сообщения.

---

## ✅ ИСПРАВЛЕНО — 3. SQLite по умолчанию — риск при деплое с несколькими workers

**Файл:** `app/config.py:4`

`database_url` по умолчанию указывает на SQLite. SQLite не поддерживает одновременные записи от нескольких Uvicorn workers. Если при деплое не задать `DATABASE_URL`, приложение молча запустится на SQLite и будет давать ошибки при нагрузке.

**Решение:** либо сделать `DATABASE_URL` обязательной переменной (без дефолта), либо явно документировать риск и выводить предупреждение при старте если используется SQLite.

---

## ✅ ИСПРАВЛЕНО — 4. Манифесты MAX Bot не описывают файловый API

**Файлы:** `MAX Bot Incoming - LLM Manifest.md`, `MAX Bot send message - LLM Manifest.md`

Входящий манифест показывает `attachment: null` в примере — вложения технически существуют, но не задокументированы. Исходящий манифест описывает только `content.type: TEXT`, эндпоинта для отправки файлов нет. Без обновлённых манифестов нельзя планировать реализацию файлового обмена.

**Решение:** получить от edna обновлённые манифесты с описанием файлового API (входящий вебхук с вложением и исходящий запрос с файлом).

---

## ✅ ИСПРАВЛЕНО — 5. Синхронный httpx станет блокером при передаче файлов

**Связано с замечанием №1.**

Файл 5–10 MB скачивается и загружается 3–10 секунд. Синхронный `httpx.post` (замечание №1) при текстовых сообщениях терпим, но при файлах заблокирует event loop на всё время передачи. Замечание №1 должно быть исправлено **до** реализации файлового обмена.

**Решение:** исправить замечание №1 (async httpx), затем добавлять файловый обмен.

## 7. Нет возможности изменить API-ключ существующего канала

**Файл:** `app/routers/api.py`, фронтенд настроек

При подключении канала API-ключ сохраняется один раз. Если ключ изменился (перевыпуск, компрометация), оператор не может обновить его — только отключить канал и создать новый, теряя историю сообщений и связку с открытой линией.

**Решение:** добавить эндпоинт `PATCH /api/channels/{channel_id}` и форму редактирования в настройках. В `ChannelResponse` api_key намеренно не возвращается — отображать в форме только последние 4 символа (`****...XXXX`).

## ✅ ИСПРАВЛЕНО — 9. Кнопка «Скопировать» для webhook URL не работает

**Файл:** `app/routers/settings_page.py` (функция `copyWebhook`)

Кнопка «Скопировать» под URL для приёма входящих сообщений из MAX Bot не копирует URL в буфер обмена. Скорее всего причина — `navigator.clipboard.writeText` не работает в iframe без разрешения `clipboard-write`, а страница настроек открывается внутри iframe Bitrix24.

**Решение:** заменить `navigator.clipboard.writeText` на fallback через `document.execCommand('copy')` — этот метод работает в iframe.

## ✅ ИСПРАВЛЕНО — 15. Валидация уникальности при подключении канала

**Файлы:** `app/routers/api.py`, `app/routers/settings_page.py`

**Правила уникальности каналов внутри одного портала Битрикс24:**

- **Sender ID** — уникален среди активных каналов портала. Один и тот же MAX Bot канал нельзя подключить дважды, пока первый активен. После отключения канала Sender ID освобождается и может быть использован снова.

## ✅ ИСПРАВЛЕНО — 6. Отправка файлов из Битрикс24 в MAX

**Файлы:** `app/routers/handler.py`, `app/routers/files.py`, `app/services/file_cache.py`

Отправка медиафайлов (IMAGE, VIDEO, AUDIO, DOCUMENT) работает.

**Итоговая архитектура:**
- Файл детектируется из `message.files[]` в вебхуке `OnImConnectorMessageAdd`
- Тип определяется по MIME-типу и расширению (`_detect_media_type`)
- Файл **немедленно скачивается с Bitrix24** при обработке вебхука и кладётся в `file_cache` (UUID-ключ, TTL 10 мин)
- edna получает URL вида `/file/<uuid>.jpg` — стабильный, без Bitrix-подписи

**Почему предзагрузка, а не прокси на лету:** edna скачивает файл асинхронно (после того, как вернула 200 OK). К тому моменту Bitrix-подпись (SIGN) в URL истекает — файл становится недоступен. Предзагрузка решает эту проблему.

**Остаточное ограничение:** кеш только в памяти. При рестарте сервера файлы теряются — если edna попытается забрать файл после рестарта, получит 404. На практике edna скачивает быстро, это не проблема.
