# Review: замечания по коду

## ✅ ИСПРАВЛЕНО — 1. Синхронные HTTP-вызовы блокируют event loop

**Файлы:** `app/services/maxbot.py:6`, `app/services/bitrix.py:15`

`httpx.post` вызывается синхронно внутри async FastAPI-хендлеров. При медленном ответе edna или Bitrix (300–500ms) event loop блокируется, и реальная пропускная способность составит 2–3 сообщения в секунду вместо требуемых 50.

**Решение:** заменить синхронный `httpx.post` на `async with httpx.AsyncClient` с `await`.

---

## 2. Ошибка отправки в MAX Bot не сообщается оператору

**Файл:** `app/routers/handler.py:202`

При сбое отправки сообщения в edna ошибка только логируется. В Bitrix24 не отправляется `imconnector.send.status.undelivered`, поэтому оператор не видит, что сообщение не доставлено. Нарушает требование PRD раздел 4.3.

**Решение:** при ошибке отправки в edna вызывать `imconnector.send.status.undelivered` с идентификаторами сообщения.

---

## ✅ ИСПРАВЛЕНО — 3. SQLite по умолчанию — риск при деплое с несколькими workers

**Файл:** `app/config.py:4`

`database_url` по умолчанию указывает на SQLite. SQLite не поддерживает одновременные записи от нескольких Uvicorn workers. Если при деплое не задать `DATABASE_URL`, приложение молча запустится на SQLite и будет давать ошибки при нагрузке.

**Решение:** либо сделать `DATABASE_URL` обязательной переменной (без дефолта), либо явно документировать риск и выводить предупреждение при старте если используется SQLite.

---

## ✅ ИСПРАВЛЕНО — 4. Манифесты MAX Bot не описывают файловый API

**Файлы:** `MAX Bot Incoming - LLM Manifest.md`, `MAX Bot send message - LLM Manifest.md`

Входящий манифест показывает `attachment: null` в примере — вложения технически существуют, но не задокументированы. Исходящий манифест описывает только `content.type: TEXT`, эндпоинта для отправки файлов нет. Без обновлённых манифестов нельзя планировать реализацию файлового обмена.

**Решение:** получить от edna обновлённые манифесты с описанием файлового API (входящий вебхук с вложением и исходящий запрос с файлом).

---

## ✅ ИСПРАВЛЕНО — 5. Синхронный httpx станет блокером при передаче файлов

**Связано с замечанием №1.**

Файл 5–10 MB скачивается и загружается 3–10 секунд. Синхронный `httpx.post` (замечание №1) при текстовых сообщениях терпим, но при файлах заблокирует event loop на всё время передачи. Замечание №1 должно быть исправлено **до** реализации файлового обмена.

**Решение:** исправить замечание №1 (async httpx), затем добавлять файловый обмен.

## ✅ ИСПРАВЛЕНО — 6. Отправка файлов из Битрикс24 в MAX

**Файлы:** `app/routers/handler.py`, `app/routers/files.py`, `app/services/file_cache.py`

Отправка медиафайлов (IMAGE, VIDEO, AUDIO, DOCUMENT) работает.

**Итоговая архитектура:**
- Файл детектируется из `message.files[]` в вебхуке `OnImConnectorMessageAdd`
- Тип определяется по MIME-типу и расширению (`_detect_media_type`)
- Файл **немедленно скачивается с Bitrix24** при обработке вебхука и кладётся в `file_cache` (UUID-ключ, TTL 10 мин)
- edna получает URL вида `/file/<uuid>.jpg` — стабильный, без Bitrix-подписи

**Почему предзагрузка, а не прокси на лету:** edna скачивает файл асинхронно (после того, как вернула 200 OK). К тому моменту Bitrix-подпись (SIGN) в URL истекает — файл становится недоступен. Предзагрузка решает эту проблему.

**Остаточное ограничение:** кеш только в памяти. При рестарте сервера файлы теряются — если edna попытается забрать файл после рестарта, получит 404. На практике edna скачивает быстро, это не проблема.

### ✅ ИСПРАВЛЕНО — SEC-4. URL файлов публичны и не имеют TTL

**Файлы:** `app/routers/files.py`, `app/services/file_cache.py`, `app/routers/handler.py`

**Что сделано:** URL файлов теперь защищён HMAC-подписью с временным ограничением.

Формат URL: `/file/{uuid}.{ext}?token=HMAC-SHA256(secret_key, "{uuid}.{ext}:{expires}")&expires={unix_timestamp}`

- Запрос без `token` и `expires` → `403 Forbidden`
- Несовпадение подписи или истёкшее время → `403 Forbidden`
- Ключ подписи — `SECRET_KEY` из переменных окружения (тот же, что для шифрования БД)
- TTL токена — **10 минут** (совпадает с TTL кеша)

**Техническое ограничение:** файлы хранятся только в памяти сервера в течение 10 минут с момента отправки оператором. По истечении этого времени URL перестаёт работать (файл удаляется из кеша). Это приемлемо, так как MAX Bot скачивает файл за секунды и хранит его на своём сервере. Долгосрочное решение — переход на S3-совместимое хранилище (см. PROD-3).

### ~~SEC-5. Ограничения на файлы~~ — Не будет исправлено

**Обоснование:** обе платформы уже валидируют файлы самостоятельно:
- **Входящие (MAX Bot → Bitrix):** edna/MAX Bot проверяет типы файлов до отправки вебхука. Если вебхук дошёл до `/incoming` — платформа его уже одобрила.

Наш сервер является прокси, а не точкой хранения или исполнения файлов. Дублирование проверок создаёт ложные срабатывания без реальной пользы для безопасности.

### ✅ ИСПРАВЛЕНО — SEC-6. Нет rate limiting

**Файлы:** `app/services/rate_limiter.py`, `app/routers/incoming.py`, `app/routers/handler.py`

**Что сделано:** in-memory sliding window rate limiter (50 req/sec).

- `/incoming/{webhook_token}` — 50 req/sec **на канал** (ключ: `webhook_token`), проверка до DB lookup
- `/handler` — 50 req/sec **на портал** (ключ: `member_id`), проверка после извлечения `member_id` из тела запроса
- При превышении → `429 {"error": "too_many_requests"}`
- GET/HEAD на `/incoming` (пинги верификации edna) не ограничиваются

**Архитектурное решение:** чистый in-memory sliding window без внешних зависимостей. slowapi не используется — для `/handler` ключ находится в теле запроса, что несовместимо с `key_func` slowapi без дублирования логики парсинга тела в middleware.

## БЛОК: НАДЁЖНОСТЬ ДОСТАВКИ

Источник: `system_feedback.pdf`. Сейчас система работает по принципу «попробовали один раз и забыли». Для продакшна нужна модель «сначала сохранить, потом доставлять с retry».

---

### REL-1. Retry отсутствует — сообщения теряются при временных сбоях

**Файлы:** `app/services/maxbot.py` (`_post`), `app/services/bitrix.py` (`call_bitrix`)

При сетевой ошибке, `429`, `5xx` или таймауте сообщение просто теряется — нет ни повтора, ни уведомления.

**Решение:** добавить retry с exponential backoff и jitter только для временных ошибок (408, 429, 500, 502, 503, 504, сетевые ошибки). Для постоянных ошибок (400, 401, 403, 404, 422) — не ретраить, сразу `failed`.

Расписание retry: 1с → 5с → 30с → 2м → 10м → 30м. После 6 попыток — статус `dead`.

---

### REL-2. `/incoming` всегда возвращает 200 OK, даже если доставка провалилась

**Файл:** `app/routers/incoming.py`

Если отправка в Bitrix24 упала, код ловит исключение, логирует и всё равно возвращает `{"status": "ok"}`. edna считает webhook доставленным и не повторяет — сообщение теряется.

**Решение:** возвращать `200 OK` только если сообщение сохранено и поставлено в очередь. Если очередь недоступна — `503`. Если payload невалидный — `400`. (Связано с #2)

---

### ✅ ИСПРАВЛЕНО — REL-3. Нет идемпотентности — при повторном webhook создаются дубли

**Файлы:** `app/routers/incoming.py`, `app/main.py`

**Что сделано:**
- `main.py` — при старте создаётся уникальный индекс БД по `(channel_id, direction, max_message_id)` для входящих сообщений
- `incoming.py` — двухуровневая защита: сначала явная проверка по `max_message_id` до вставки (быстрый путь), затем перехват `IntegrityError` при одновременных запросах (race condition). Оба случая возвращают `200 OK` и логируют `duplicate message id=...`

**Примечание:** идемпотентность для исходящих (Bitrix → edna) не реализована — там другой механизм защиты через anti-replay в SEC-2.

---

### REL-4. Нет очереди — отправка происходит прямо внутри HTTP handler

**Файлы:** `app/routers/incoming.py`, `app/routers/handler.py`

Внешний API (edna или Bitrix24) вызывается синхронно внутри обработчика входящего запроса. Если внешний сервис временно недоступен — сообщение теряется, нет возможности повторить.

**Решение (минимальный вариант):** таблица `message_delivery_tasks` в БД со статусами `pending → processing → sent / failed / dead`, счётчиком попыток, временем следующей попытки и последней ошибкой. Фоновый worker обрабатывает очередь. HTTP handler только сохраняет задачу и возвращает `200 OK`.
