# Telegram из сделки по телефону: идентичность клиента

Дата: 20.11.2026. Новая задача владельца после приёмки контакта/сделки по входящему Telegram. Это исследование и критерии реализации; код исходящей CRM-отправки Telegram ещё не включён, commit/push/deploy не выполнялись.

## Обязательный сценарий

На одном портале подключены MAX и Telegram. Контакт A создан вручную с телефоном; ему уже писали через MAX. Клиент написал через Telegram без телефона: появились контакт B, сделка и диалог по Telegram ID. Компания отправляет из сделки контакта A сообщение в Telegram по телефону. Получатель оказывается владельцем Telegram ID контакта B.

Требуется сохранить сообщения, историю обоих каналов и сделки; ответ Telegram должен отправляться через исходный Telegram-канал. Совпадение личности не означает объединение сделок или технических диалогов. Отправка не должна дублироваться из-за ошибки CRM-сопоставления или изменения контакта.

## Что проверено

Методы Битрикс проверены через b24-dev-mcp. Сервер предоставляет документацию, а не доступ к данным портала.

| Возможность | Результат проверки |
|---|---|
| `messageservice.sender.add` | Позволяет зарегистрировать отдельный провайдер Telegram в уже используемом механизме отправки по телефону. Сам по себе не сопоставляет телефон с Telegram ID. |
| `imopenlines.crm.chat.get` | Читает чаты объекта CRM, возвращает CHAT_ID, CONNECTOR_ID, CONNECTOR_TITLE. Для проверки истории закрытых чатов нужен ACTIVE_ONLY=N. Это не метод перепривязки чатов. |
| `crm.duplicate.findbycomm` | Ищет CRM-объекты по PHONE/EMAIL. Telegram ID как тип поиска не поддержан. Контакт B без телефона этим поиском не обнаружить. |
| `crm.entity.mergeBatch` | Объединяет объекты одного типа, основным становится первый ID. Остальные объекты удаляются после успеха. Возможны SUCCESS, CONFLICT и ERROR. Метод не доказывает, что выбранные контакты принадлежат одному человеку. Само наличие метода не подтверждает сохранность конкретных привязок нашего коннектора после объединения. |

Штатный чат-трекер Битрикс связывает обращения из разных каналов по общим контактным данным. В линии должны быть включены «Проверять клиента по базе CRM» и «Использовать чат-трекер». Документация не является доказательством автоматического разрешения именно случая двух уже существующих карточек при позднем появлении телефона: необходима предпродовая проба.

Telegram-коннектор после c69a606 работает с CHAT_GROUP=False; входящие передают достоверный PHONE при его наличии и не устанавливают disable_crm. Это предпосылки штатного сопоставления, а не готовая гарантия объединения.

## Критическая граница edna

В актуальной документации отправки Telegram по PHONE ответ содержит outMessageId и phone. TELEGRAM_ID в этом ответе не обещан. Нельзя связывать эту отправку с последним Telegram-диалогом по времени, имени или факту доставки.

Нужна проверенная связь PHONE ↔ TELEGRAM_ID: например, оба идентификатора одного получателя в реальном входящем webhook. Приход только TELEGRAM_ID подтверждает адрес ответа, но не его принадлежность CRM-контакту A.

Документированный `/api/subscribers/get-by-address` в просмотренной статье принимает EXT_USER_ID, который задавался при создании получателя. Использование этого метода как произвольного поиска Telegram ID по телефону не подтверждено. Не реализовывать такой обход по догадке.

## Порядок реализации и проверки

1. Переиспользовать механизм CRM MAX: отдельный provider CODE для каждого Telegram-канала, сохранённые bindings сделки/контакта, нормализация выбранного телефона, очередь, корреляция статусов, запрет слепого повтора при uncertain. MAX/MAX Bot/CRM MAX не менять по смыслу. Не выбирать отправителя по последнему сообщению клиента.
2. Поддержать текст Telegram по PHONE отдельным адаптером; ответ по TELEGRAM_ID в существующей Открытой линии сохранить. Не подменять прежние user.id/chat.id телефонным номером.
3. На предпроде воспроизвести две карточки A/B до отправки. Зафиксировать их ID, обе сделки, существующий Telegram-диалог, настройки CRM/чат-трекера. Получить обезличенные структуры ответа отправки, статусов и входящего ответа.
4. Проверить, прислала ли edna достоверную пару PHONE + TELEGRAM_ID и как Bitrix обработал поздний телефон существующего клиента. Проверить привязки чатов A/B через imopenlines.crm.chat.get с ACTIVE_ONLY=N. Не делать вывод об объединении только по HTTP 200 или показанному имени.
5. Пока связки нет, продолжать доставлять ответ в исходный Telegram-диалог. Сохранять факт отправки в исходной сделке. Не утверждать, что контакты объединены, и не создавать повторную сетевую отправку ради сопоставления.
6. Если связка подтверждена, но контакты остались раздельными, определить дальнейшее действие по результатам пробы. Базовое безопасное поведение – сохранить карточки и использовать штатное ручное объединение в CRM. Автоматический merge не включать молча: это отдельная операция удаления карточек и выбора основных данных. В случае CONFLICT нужен штатный разбор конфликта.
7. После любого штатного объединения отдельно проверить обе истории, обе сделки, входящие/исходящие через MAX и Telegram, переименование, поздние статусы уже отправленных сообщений, повтор callback и рестарт worker. Сохранённые bindings старых CRM-отправок не переписывать без подтверждённого сопоставления.

Приёмка исходящего Telegram из сделки включает этот сценарий. Если возможна только ручная привязка или edna не отдаёт связку, ограничение нужно явно обсудить с владельцем до объявления полной готовности.
