# Telegram: изображения и документы – локальная реализация

Актуально на 19.11.2026. База – `8ed004f`. Изменения только локальные: commit, push, Amvera и промышленный контур не затрагивались. Это не акт живой приёмки.

## Реальные входящие примеры

Владелец передал четыре webhook: IMAGE и DOCUMENT, каждый с подписью и без неё. Файл находится в `messageContent.attachment`: `url`, `name`, `size` в байтах. Подпись находится в `messageContent.caption`, а `text` пустой. MIME в webhook отсутствует; он проверяется по HTTP-ответу и сигнатуре содержимого. Источник в примерах – HTTPS на `app.edna.ru`.

Обезличенные структуры сохранены в `tests/fixtures/telegram_media_incoming.json`. Заменены отправитель, идентификаторы, имена и файловые URL; исходные размеры сохранены. Настоящие файлы владельца агент не скачивал. Самый большой пример – PDF размером 50 825 835 байт, поэтому прежний черновой предел 10 МБ заменён на 64 МиБ (67 108 864 байта). Это защитный предел приложения, не подтверждённый предел Telegram/edna. В пользовательском предупреждении используется обозначение «64 МБ».

| Контент | Данные от владельца | Состояние приложения |
|---|---|---|
| IMAGE | Реальные webhook с подписью и без неё | Приём и отправка реализованы локально; живую доставку после выкладки проверить. |
| DOCUMENT | Реальные PDF с подписью и без неё, включая 50,8 МБ | Приём и отправка реализованы локально; проверить настоящий большой файл и имя у получателя. |
| Аудиофайл | По сообщению владельца придёт как прикреплённый файл; примера пока нет | Следующий этап; пока предупреждение/отказ. |
| Голосовое с микрофона, стикер | По проверке владельца не поддерживаются; webhook-примеров нет | Поддержка не обещается; если неизвестный тип всё же придёт, показывается предупреждение. |
| Видео | Возможно поддерживается; webhook пока не получен | Не включено до подтверждения. |
| LOCATION | Есть реальные longitude/latitude, address=null | Контракт зафиксирован; пока предупреждение, реализация позже. |
| CONTACT | Есть данные чужого контакта | Пока предупреждение. Этот телефон не подменяет личность отправителя и не передаётся как его CRM-телефон. |
| Reply | Пришёл TEXT, все reply-поля null | Передаётся текст. Связь с цитируемым сообщением по этому примеру восстановить нельзя. |

## Что изменено

- Telegram скачивает файл до подтверждения webhook/события и сохраняет его вместе с сообщением и задачей одной транзакцией. В очередь не попадают API-ключи, OAuth и исходные подписанные ссылки.
- Новая таблица `telegram_files` хранит содержимое, MIME, исходное имя, срок хранения и связь с сообщением. Её добавляет существующий `metadata.create_all` под блокировкой миграции; существующие таблицы/колонки не перестраиваются. Файлы доступны другому worker и после перезапуска.
- Срок хранения – семь суток. Очистка выполняется при сохранении новых файлов и раз в час в worker, даже без новых вложений. По окончании срока выдача запрещена сразу. Удержанная входящая задача передаст подпись с предупреждением; исходящая завершится ошибкой с уведомлением.
- Существующий HMAC-формат `/file/...` и TTL ссылки 10 минут сохранены. Для Telegram ключ начинается с `tg-`; каждая попытка доставки получает свежую ссылку. Старый кеш и незавершённые MAX-задачи не меняются. Ответ включает исходное имя и запрет MIME-sniffing; TTL ссылки не продлевает срок хранения.
- Скачивание только по HTTPS: входящие – `app.edna.ru`, исходящие – точный хост сохранённого REST endpoint авторизованного портала. CDN пока не разрешён автоматически. Каждый redirect проверяется заново; внутренние/служебные IP запрещены. Проверенный IP используется для соединения напрямую, TLS проверяет исходное имя хоста. Прокси окружения не используются. Поток ограничен 64 МиБ, проверяется также Content-Length; тайм-аут – 120 секунд.
- Начальный набор: JPEG, PNG, GIF, WebP; PDF, DOC/DOCX, XLS/XLSX, PPT/PPTX, UTF-8 TXT/CSV. Проверяются имя, фактический MIME и сигнатура/контейнер. Это не антивирусная проверка. Другие форматы получают явный отказ/предупреждение. Содержимое файлов не исполняется и архивы не распаковываются.
- Входящие передают подпись и файл вместе через `imconnector.send.messages`. CRM-трекер, Telegram ID, имя и общая линия сохранены. Временный сбой скачивания даёт 503 без сохранения неполной операции; постоянный отказ сохраняет обращение с подписью и предупреждением.
- Исходящие поддерживают **один файл на сообщение**. Несколько файлов отклоняются целиком с уведомлением «прикрепите по одному»; первый файл отдельно не отправляется. Повтор события с обновлённым SIGN не повторяет скачивание/отправку; смена файла под тем же IM id отклоняется.
- По решению владельца подпись отправляется как в MAX: `content.text` вместе с `IMAGE`/`DOCUMENT`. Документация Telegram edna не описывает `text` у медиа: приёмка подписи остаётся открытой, автоматической повторной отправки отдельным текстом нет. API ограничивает `name` 25 символами: метаданные сокращаются с сохранением расширения; полное имя остаётся в БД и Content-Disposition. Сохранность имени у клиента проверить.
- После неопределённого POST нет слепого повтора. Статусы и READ используют прежнюю корреляцию. Проверка визуального прочтения остаётся отложенной, её логика не менялась.
- Файловые URL в Telegram JSON-диагностике сохраняют только схему и хост: скрыты и путь, и query. Исключение для полных runtime-путей incoming/status сохранено.

## Проверки и дальнейшая приёмка

Полный прогон – **179 тестов OK без пропусков**, включая проверки на изолированной временной PostgreSQL 16. Включены реальные обезличенные структуры, синтетические байты, повторная миграция, гонка двух одинаковых медиа-webhook, атомарность, сохранность файла между сессиями, истечение хранения, HMAC, SSRF/redirect, ограничение потока, чтение настоящим HTTP-парсером с Connection: close и отсутствие повторной отправки при неопределённом результате. PostgreSQL остановлена и удалена. Рабочая БД и `.env` не использовались. Реальные 50,8 МБ в этом прогоне не скачивались: это отдельный критерий живой приёмки.

Статические проверки: AST всех 50 Python-файлов совместим с Python 3.11, Node-проверки CRM/Telegram UI и optional Subject ID прошли, `git diff --check` чист. Прежние локальные правки сохранены. На стенде нужны те же четыре входящих случая и исходящие изображение/PDF, с текстом и без него; проверить открытие, полное имя и большой файл. Если исходящий Bitrix URL ведёт на CDN, сначала установить настоящий контракт доверенного источника, не снимать SSRF-защиту. При исчезнувшей подписи остановить приёмку этого сценария и согласовать отдельный текст либо подтверждённое поле API.

Новая таблица увеличивает объём БД; перед промышленной поставкой оценить частоту файлов и доступное место, сохранить штатную резервную копию. Для большого объёма выделенное объектное хранилище остаётся следующим решением. Откат на `8ed004f` с новыми ожидающими медиа-задачами небезопасен: старый worker не умеет их доставлять. Сначала остановить новые операции и разобрать/завершить очередь; таблицу и файлы автоматически не удалять. Прод обновляет команда edna отдельно.

[Отправка Telegram edna](https://docs-pulse.edna.ru/docs/api/messages/regular-messages/sending-telegram) подтверждает IMAGE/DOCUMENT, HTTPS, URL до 1000 символов и `name` до 25 символов; не доказывает доставку подписи.
