# Telegram – идентификаторы, имена, CRM и статусы

Актуально на 20.11.2026. Рабочая памятка для будущих изменений Telegram и общей логики MAX/MAX Bot/CRM MAX. Здесь собраны итоговые правила и результаты приёмки; промежуточные предположения из журналов не заменяют их. При изменении поведения обновлять этот документ вместе с кодом и результатами проверки.

**Решение владельца 20.11.2026:** Telegram в формате MVP считать готовым с известными ограничениями. Это не означает промышленную выкладку, успешные все виды медиа или живую приёмку ещё не выложенной правки CRM-имени. Сводный список открытых вопросов – раздел 14.

## 2. Идентификаторы нельзя смешивать

| Поле | Значение и применение |
|---|---|
| `subscriber.id` | Внутренний ID получателя в edna. Это не TELEGRAM_ID и не MAX_ID. |
| `subscriber.identifier` | Основной адрес в конкретном webhook. В Telegram проверяем типизированный массив, а не угадываем тип по этому полю. |
| `subscriber.identifiers[].type=TELEGRAM_ID` | Числовой ID Telegram-аккаунта. Устойчивый адрес ответа; хранится строкой. |
| `TELEGRAM_USERNAME` | Необязательный username для отображения. Не используется как ID личности или адрес ответа. |
| `PHONE` | Телефон, только если достоверно получен от edna или выбран для CRM-отправки. Не подставлять Telegram ID вместо номера. |
| `outMessageId` | Созданный и сохранённый приложением ID исходящей отправки. |
| `requestId` в статусе | Сопоставляется с сохранённым outMessageId и каналом. |
| `messageId` в статусе edna | ID сообщения edna, не клиента. Не использовать для определения Telegram-аккаунта. |
| `im.chat_id`, `im.message_id` | Внутренние ID чата и сообщения Битрикс, необходимые для READ Открытой линии. |
| CRM contact/deal ID | ID карточек CRM. Не выводятся из Telegram ID, номера сообщения или названия диалога. |

Числовые ID не преобразовывать через JavaScript Number: возможна потеря точности. Username может отсутствовать или меняться; это не новый клиент.

В подтверждённых webhook Telegram одновременно приходили PHONE+TELEGRAM_ID, иногда также TELEGRAM_USERNAME; `userInfo` был null. Это достоверная связь идентификаторов данного получателя в edna. Совпадение имени, времени ответа или последней исходящей отправки такой связью не является.

## 3. Техническая личность и маршрут ответа

Telegram использует отдельный коннектор `edna_telegram` на общей выбранной Открытой линии приложения. MAX/MAX Bot сохраняют свой коннектор `max_bot`.

- Telegram `user.id` – `tg:<TELEGRAM_ID>`.
- Внешний Telegram `chat.id` – `tg:<первые 32 hex SHA256(sender)>:<TELEGRAM_ID>`.
- Переименование не меняет эти ID. При том же sender и Telegram ID внешний chat.id не меняется после переподключения канала.
- Привязка исходящего ответа проверяется по порталу, коннектору, линии и сохранённому диалогу. Получателя и отправителя не выбирать по имени, телефону другого чата или последнему активному каналу.
- Ответ из Telegram-диалога отправляется на TELEGRAM_ID через тот же Telegram-отправитель. Ошибка одного отправителя не даёт права переключиться на другой или на MAX.

Для MAX/MAX Bot сохраняются исторические форматы: у legacy MAX Bot внешний chat.id – исходный identifier, у остальных MAX-каналов – `<sender>:<identifier>`. В `user.id` MAX/MAX Bot обычно передаётся subscriber.id edna, с прежним fallback на identifier. Не унифицировать эти форматы с Telegram задним числом: это может потерять прежние диалоги и маршруты.

В модели `Message.bitrix_chat_id` исторически хранятся разные виды ID: для входящего Telegram – внешний chat.id, для исходящего из Открытой линии – внутренний im.chat_id. Перед использованием проверять направление и путь создания записи; не считать поле универсальным CRM/chat ID.

## 4. Имена клиента и название диалога

Единый алгоритм в новой локальной правке:

1. Валидный TELEGRAM_USERNAME из текущего webhook, без добавленного приложением `@`.
2. Доступное имя из userInfo; поля проверяются в порядке firstName, displayName, userName.
3. Сохранённое имя последнего входящего того же Telegram ID в том же локальном канале.
4. Техническое название `Telegram <ID>`.

Для username фамилия не добавляется, в том числе из старой записи. Для нового имени из userInfo используется его собственная lastName, а не фамилия другой записи. При использовании истории сохраняется её пара имя/фамилия. Для реального имени название чата включает фамилию, если она есть. Начальная доставка и отложенное переименование используют один builder названия.

Если webhook не содержит username, его не выдумываем и не получаем отдельным неподтверждённым запросом. У клиента 1 username стабильно приходил, у клиента 2 PHONE+TELEGRAM_ID приходили без username. Предположение «username отсутствует, потому что компания начала переписку по телефону» не доказано: у клиента может не быть публичного username или edna может не передавать его.

История имени сейчас ищется по локальному channel_id, а не произвольно между Telegram-отправителями. Стабильность внешнего chat.id при переподключении сама по себе не означает, что новый локальный Channel найдёт старое отображаемое имя.

## 5. Название чата не должно становиться выдуманной фамилией CRM

Есть разные объекты: заголовок диалога, внешний посетитель Битрикс и CRM-контакт. Они могут отображаться похоже, но это не одно поле.

В выложенном cbcf37d технический `Telegram <ID>` передавался как user.name. На скриншотах Битрикс показал профиль посетителя с именем Telegram и фамилией <ID>, а у существующего CRM-контакта сохранил исходное имя, но добавил ID к отображаемому имени. Это дефект, а не успешное получение имени клиента.

Технический заголовок с ID оставляется только в chat.name. Первая попытка защиты в 6a17434 исключала user.name/last_name при заглушке; владелец подтвердил сохранность восстановленного CRM-имени в этом тесте, но Bitrix переименовал внешнего участника в «Гость». Как целостное решение отображения этот вариант не принят, несмотря на успешные моки.

В следующей локальной корректировке для заглушки явно передаётся одно нейтральное слово user.name=Telegram, без ID и без user.last_name. Это не полученное имя клиента, а метка неизвестного внешнего пользователя, предотвращающая пустое имя. Заголовок чата остаётся `Telegram <ID>`. Правило работает и для старых задач без новой схемы БД. Достоверный телефон, user.id и chat.id передаются как прежде; CRM-трекер не отключается. Реальное имя или username при их наличии по-прежнему передаются как данные внешнего пользователя.

На живом портале ещё нужно подтвердить, что участник перестал быть «Гостем», реальные имя/фамилия CRM сохранились, а Битрикс не возьмёт ID из уже сохранённого профиля посетителя или chat.name. Отдельно проверить нового клиента без телефона/имени. Не объявлять защиту CRM-имени принятой только по мокам. Если нужно показывать именно имя существующего CRM-контакта при отсутствии данных edna, это отдельное получение CRM-данных с проверкой прав; текущий imopenlines-запрос не даёт универсального переключателя такого поведения.

Уже изменённые фамилии автоматически не очищаем: исходное значение неизвестно, а числовая часть сама по себе не доказывает происхождение. Восстановление конкретной карточки – отдельное действие после проверки полей. Не удалять контакты/историю ради восстановления названия.

## 6. Переименование выполняется отдельно от доставки

Изменение известного имени создаёт отдельную долговечную задачу `telegram_rename`. Она ждёт успешной доставки соответствующего входящего, затем вызывает imconnector.chat.name.set с CONNECTOR, LINE, CHAT_ID, USER_ID и NAME. USER_ID нужен для личного режима коннектора.

Сбой переименования не повторяет сообщение клиента. Блокировка на диалог и сравнение с последним известным именем не позволяют старой задаче затереть более новое имя. Ручное или автоматическое переименование не должно менять адрес клиента, sender или историю.

## 7. Контакт и сделка по входящему

Telegram зарегистрирован с **CHAT_GROUP=False**: это личный чат. В прежнем групповом режиме CRM-трекер входящих не запускался, из-за чего контакт/сделка не создавались ожидаемым способом. Исправление режима принято владельцем.

Приложение передаёт настоящее входящее через imconnector.send.messages и не выставляет disable_crm. Нужные контакт/сделку создаёт или находит штатная CRM-логика общей линии согласно её настройкам. Важны «Проверять клиента по базе CRM», чат-трекер и выбранный режим создания сущностей. Без проверки настроек нельзя обещать одинаковый CRM-результат на любом портале.

Во входящем запросе приложения не задаётся ID целевой сделки. Совпадение телефона помогает штатному сопоставлению, но из него нельзя вывести факт автоматического объединения двух уже существующих CRM-карточек.

В нашей БД нет самостоятельного справочника клиентов и универсальной таблицы связей контакт ↔ телефон ↔ MAX ID ↔ Telegram ID. Хранятся сообщения, адреса/типы, каналы, задачи и CRM-исходящие с bindings. Подхватывание имени между MAX/MAX Bot по известному identifier – не объединение CRM-контактов.

Автоматического merge контактов/сделок в приложении нет. Найти дубли по телефону и объединить контакты – разные операции; merge может удалить вторичные карточки и вернуть конфликт. Не запускать его как скрытый побочный эффект отправки. Один человек может иметь разные сделки и отдельные MAX/Telegram-диалоги.

## 8. Первое Telegram-сообщение из сделки по телефону

Используется прежний механизм CRM MAX: отдельный messageservice-провайдер на канал, `/crm/messages/send`, атомарное сохранение CrmOutgoingMessage и задачи отправки.

- Telegram provider CODE – `edna_telegram_<channel.id>`; MAX – прежний `edna_max_<channel.id>`. MAX Bot в этот CRM PHONE-сценарий не включён.
- Выбранные телефон, provider, канал и исходные bindings сделки/контакта сохраняются. Не заменять их по результату следующего входящего без достоверного основания.
- Телефон нормализуется в международный формат. Пустой/недопустимый телефон не превращается в Telegram ID или username.
- Telegram CRM поддерживает TEXT до 4096 символов; MAX сохраняет прежний предел 4000. Вложения из CRM в этот выпуск не входят.
- Запрос идёт на Telegram API с to.type=PHONE и сохранённым outMessageId. Ответ оператора из уже существующего Telegram-диалога использует TELEGRAM_ID.
- В подтверждённом ответе на отправку по PHONE есть outMessageId и phone, без Telegram ID. Сам факт отправки не раскрывает Telegram ID получателя.
- Первый CRM-исходящий не копируется автоматически в историю Открытой линии. Новый диалог появляется по настоящему входящему, без фиктивного сообщения клиента.

Приложение проверяет application_token, портал, принадлежность provider и канала, активность и готовность отправителя. Уже используемые messageservice/imopenlines сохраняются; нового CRM-scope для поиска или слияния контактов не добавляли.

## 9. Очередь, повторы и неопределённый результат

Входящие, исходящие, статусы и переименование имеют постоянные задачи. Повтор webhook/CRM-callback не должен создавать повторную отправку. Для Telegram входящих дедупликация включает канал и внешний ID сообщения; для CRM – портал, provider и Bitrix message_id.

Попытка CRM-отправки фиксируется до сетевого POST. HTTP 200 означает принятие edna, а не получение или прочтение клиентом. Тайм-аут после возможной передачи запроса, потеря ответа, несовпадающий outMessageId или возвращённый адрес дают uncertain; автоматический новый POST запрещён. Поздний реальный статус может уточнить исход.

Подтверждённый отказ соединения и явный Telegram HTTP 429 допускают повтор с прежним outMessageId. Политику Telegram не переносить автоматически на MAX: его существующая обработка ошибок сохраняется. Ошибка обновления CRM-статуса повторяет только обновление статуса, а не доставку текста.

## 10. CRM-статусы и READ Открытой линии

Для одного Telegram-канала callback общий, но два независимых пути:

| Источник отправки | Как обрабатывается статус |
|---|---|
| CRM из сделки/контакта | requestId ищется в CrmOutgoingMessage того же канала/портала; обновляется messageservice.message.status.update. READ хранится как read, в CRM передаётся поддерживаемый delivered. |
| Ответ оператора из Открытой линии | requestId ищется в исходящем Message; только READ вызывает imconnector.send.status.delivery с внутренними im ID, внешним chat.id, CONNECTOR и сохранённой LINE. |

В Telegram callback сначала проверяется CRM-корреляция, затем путь Открытой линии. CRM READ не должен отмечать прочитанным чужое сообщение в чате. SENT/DELIVERED не выдаются за «Просмотрено» Открытой линии. Повторы и запоздавшие статусы не отменяют достоверное прочтение/доставку.

При сравнении использовать числовую LINE и реальные ID из событий, а не текст «Открытая линия 7» в заголовке: видимое имя линии не гарантирует её числовой ID.

Визуальный READ подтверждён владельцем в старом и новом Telegram-диалогах после перехода в личный режим. Это согласуется с гипотезой о влиянии CHAT_GROUP, но отдельного контролируемого сравнения режимов не было. Переименование не откатывали, READ дополнительно не меняли. Не возвращаться к версии «переименование сломало READ» без новых данных и не считать этим заново проверенным MAX.

## 11. Проверенные сценарии и исправленная трактовка теста

На предпроде подтверждены выбор Telegram-отправителя из сделки, получение текста по телефону, CRM-статусы, ответ клиента с PHONE+TELEGRAM_ID, повторное обращение после полного закрытия прежнего диалога и правильная CRM-привязка в проверенных случаях.

Отдельно проверен человек, с которым раньше общались через MAX/MAX Bot, но не через Telegram. Компания написала из его собственной сделки по телефону. Ответ открыл Telegram-диалог в этой же правильной сделке; новая сделка не создана, нового контакта по наблюдению владельца нет. Проверка выявила дефект имени-заглушки, описанный выше.

Ранее агент ошибочно трактовал это как привязку к сделке другого тестового человека. Владелец исправил трактовку. **Подтверждённого дефекта привязки к чужой сделке в этом тесте нет.** Старые записи об этом в журналах – история недоразумения.

Наблюдения не доказывают автоматический merge двух CRM-карточек и не заменяют проверки всех ролей, нескольких порталов/отправителей/телефонов, ошибок и гонок. Для клиента, сначала известного только по Telegram ID, а затем по телефону, сохранять старый технический диалог; отдельно проверять результат штатного CRM-сопоставления и историю.

## 12. Переключатели, безопасность и ограничения

`TELEGRAM_ENABLED` удалён; его старые значения игнорируются. Telegram в Открытых линиях от него не зависит. Наличие Telegram-каналов, включая отключённые, сохраняет административные проверки и правильную авторизацию установки; MAX-only установки не должны получать несовместимое новое поведение.

`CRM_TELEGRAM_OUTREACH_ENABLED` – другой параметр, только для исходящего Telegram из CRM, по умолчанию 0. На предпроде владелец включил его. Дополнительно нужны прежние условия CRM: CRM_OUTREACH_ENABLED, готовая авторизация портала, ожидаемый CODE приложения и выданный messageservice. Отсутствие messageservice блокирует CRM-отправку, но не Открытую линию Telegram.

При остановке CRM Telegram worker не начинает новые Telegram CRM POST; сверка убирает его провайдеры и завершает ещё не начатые отправки с ошибкой. Принятые сообщения, поздние статусы, Telegram-входящие/ответы и CRM MAX сохраняются. Не отключать общий коннектор ради одного канала и не менять чужие callback.

Ограничения медиа остаются: входящие изображения/PDF и локация приняты в проверенных сценариях; edna, по сообщению владельца, не передаёт входящее видео; исходящие PDF/изображения не доставлялись и напрямую из Postman с публичными URL. Исходящее аудио не проверено. Новый успешный текст или READ эти ограничения не снимает.

Не переносить реальные телефоны, usernames, API/OAuth-секреты и секретные webhook URL в публичные документы/fixtures. Для имён действуют санитарная обработка и защита от BBCode. Не менять исторические MAX URL, формат ID, шифрование, очередь или файлы ради Telegram. Не импортировать app.main для пассивной проверки: импорт выполняет изменения БД, запуск включает worker.

## 14. Открытые вопросы после готовности MVP

| Вопрос | Что известно | Что сделать |
|---|---|---|
| CRM-имя и единые названия | 6a17434 убрал синтетическое user.name, но живьём появился «Гость». Корректировка с нейтральным Telegram без ID/фамилии локальная; защита CRM-полей ещё не принята. | Принять имя участника, сохранность реальных CRM-полей, нового клиента без имени/телефона и переименование. Уже испорченные поля не восстанавливать массово. |
| Ручной Subject ID – временный обход | Тестовый `/api/channel-profile` не вернул Telegram; types=TELEGRAM дал 400. Используется необязательное ручное поле. Успех callback не доказывает соответствие Sender/Subject и тип канала. | Уточнить у edna штатное обнаружение Telegram и способ проверки Sender ↔ Subject ↔ type. Затем убрать обход без потери каналов/истории. |
| Исходящие IMAGE/PDF | Не доставлялись даже напрямую из Postman с публичными файлами, после HTTP 200 приходил UNDELIVERED. Смена нашего файлового хранилища на кэш MAX не помогла. | Передать edna уже собранные requestId/время/ошибки и выяснить требования к загрузке URL. Корень отказа не установлен. |
| Подпись исходящего медиа | По решению владельца отправляется content.text вместе с IMAGE/DOCUMENT, аналогично MAX; Telegram-контракт подписи отдельно не принят. | Уточнить у edna поддерживаемое поле и проверить отображение подписи после восстановления доставки файла. Не считать контракт MAX доказательством. |
| Входящее видео и прочие типы | По сообщению владельца edna не передаёт входящее видео; рабочего VIDEO payload нет. Голосовые с микрофона/стикеры по прежней проверке не поддерживаются; исходящее аудио не проверено. | Получить у edna актуальную матрицу типов/направлений и реальные webhook-примеры. Аудиофайл, голосовое и видео проверять отдельно. |
| Username и связь PHONE ↔ TELEGRAM_ID | В одних webhook есть username, в других нет; оба варианта могут содержать телефон и Telegram ID. Первый ответ отправки по телефону ID не раскрывает. | Уточнить, когда доступны username/имя/телефон и есть ли штатный способ получить подтверждённую связку. Инициатор переписки как причина отсутствия username не доказан. |
| Повтор outMessageId и uncertain | Приложение не повторяет POST после неоднозначного исхода. Серверная гарантия дедупликации одинакового outMessageId и штатная сверка отправки не подтверждены. | Уточнить у edna срок/область идемпотентности и способ узнать итог по ID отправки; до этого сохранять консервативную очередь. |
| Временный media legacy cache | Диагностический TELEGRAM_MEDIA_LEGACY_CACHE_CHANNEL_ID остался в коде; рекомендован 0/удаление из окружения, выполнение не подтверждено. | Проверить, что режим выключен. После закрытия диагностики удалить временную ветку, не затронув кэш MAX. |
| Большие файлы и файловое хранение | Предел Telegram-файлов в приложении 64 МиБ, хранение в БД семь суток; большой входящий PDF 50,8 МБ отдельно живьём не принят. | Проверить реальные лимиты edna, большой файл и эксплуатационные объёмы БД/очистку. Текущие пределы приложения не выдавать за лимиты edna. |
| Объединение и история CRM | Нет нашей общей карты идентификаторов и автоматического merge. Первый CRM-исходящий остаётся в таймлайне сделки и не зеркалируется в Открытую линию. | При необходимости отдельно решить обработку двух уже существующих карточек и зеркалирование без повторной отправки клиенту. Это ограничения MVP, а не подтверждённая поломка текущего сопоставления. |
| Интерфейс CRM | Используется messageservice TYPE=SMS, поэтому возможны штатные подписи «СМС», хотя сообщение идёт в Telegram. | Учитывать как ограничение текущего механизма Битрикс; другой интерфейс – отдельная задача. |

Визуальный READ Telegram и удаление TELEGRAM_ENABLED больше не являются открытыми вопросами для проверенных сценариев. Расширенная регрессия разных порталов/ролей/каналов и промышленный выпуск остаются отдельными работами, не временными обходами API.
