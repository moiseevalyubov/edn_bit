# План разработки Telegram через edna Pulse

**Дополнение 19.11.2026 – временное подключение по Subject ID:** этап 1 уже выложен на Amvera; живой тест показал отсутствие Telegram в общем списке и HTTP 400 на types=TELEGRAM. Владелец подтвердил `code=ok` при ручной scoped-настройке callback с Subject ID. Реализован временный путь: обязательные название/ключ/Sender, необязательный Subject ID; сначала прежний список, ручной ID только если точного Sender нет. Найденный профиль имеет приоритет. Форма отправляется и с пустым Subject ID; без найденного профиля пустой ID даёт понятный отказ. Ошибки доступа/сети не обходятся, неопределённая ручная настройка не сохраняет канал. Subject ID хранится в существующем поле, не выводится в таблице. Подробный алгоритм, ограничения пары Sender ↔ Subject и условие удаления обхода – в [review.md](../review.md). Старые формулировки «не выложено» ниже относятся к первоначальному плану.

Дата: 19.11.2026. Требования: [PRD, раздел 4.9](PRD.md#49-telegram-через-edna-pulse).

Статус на 19.11.2026: первый этап реализован локально, 123 изолированных теста пройдены, включая PostgreSQL; живая приёмка и выкладка не выполнялись. Результат и ограничения: [TELEGRAM_STAGE1_PROGRESS.md](TELEGRAM_STAGE1_PROGRESS.md). Этапы 2–3 остаются планом. По подтверждению владельца MAX/MAX Bot и отправка MAX из CRM с последними исправлениями приняты на проде. Локальные документы и правки имеют приоритет перед прежним текстом GitHub; локальный HEAD `bcbdbb1` не доказывает точный состав промышленного образа.

## 1. Что и в каком порядке делаем

Сохраняем предложенные три этапа. Первую проверку API включаем в этап 1, чтобы подтвердить адресацию клиента до расширения общей обработки.

| Этап | Результат | Условие завершения |
|---|---|---|
| 1. Канал и текст | Подключение в форме, общая линия приложения, входящий текст, ответ по Telegram ID, штатный CRM-контакт | Реальный двусторонний обмен без телефона; повторное обращение того же клиента; пройдена регрессия старых интеграций. |
| 2. Другие типы | Изображения, файлы/документы, аудио, видео, голосовые, геолокация в пределах подтверждённых возможностей | Матрица по каждому направлению, реальные вложения у получателя, обработка недоступного файла и перезапуска без скрытой потери. |
| 3. Исходящий из CRM | Первый текст по телефону из раздела «Сообщение» контакта, статусы, ответ в Открытой линии | Правильный отправитель/телефон/CRM-история; подтверждена связь ответившего клиента или отдельно согласовано ограничение ручной привязки. |

По уточнению владельца **линия общая**, как сейчас. Ни новых полей выбора линии у канала, ни миграции маршрутизации старых каналов не требуется. При смене общей линии проверяем работу обоих коннекторов и сохраняем адресацию уже начатых диалогов по сохранённым данным.

План основан на существующем сегменте и сценариях PRD, а не на новом исследовании рынка. Решение – расширить существующее приложение адаптером Telegram: самостоятельное приложение дублировало бы форму, очередь, авторизацию и поддержку; ручная переписка в Telegram не выполняет требование работы из CRM. Общую инфраструктуру переиспользуем, массовую переработку MAX не включаем. Бизнес-эффект на продажи остаётся гипотезой; техническая приёмка проверяет доставку и отсутствие ручного переноса переписки.

## 2. Что подтверждено, а что остаётся риском

Проверены официальные материалы edna и справочник Битрикс24 через b24-dev-mcp. Это проверка контрактов, не доступ к клиентским порталам и не результат живой Telegram-пробы.

| Входное предположение | Статус на 19.11.2026 | Самая короткая проверка |
|---|---|---|
| Telegram похож на MAX | Отправка похожа по форме запроса; полная совместимость не подтверждена | Получить обезличенные channel-profile, входящий текст и статус с тестового Telegram-канала, сопоставить поля. |
| У входящего может быть только Telegram ID | Требование поддержать этот случай; точный payload неизвестен | Сообщение от тестового клиента со скрытым телефоном, ответ ему из Открытой линии. |
| Битрикс24 автоматически создаст контакт без телефона | Зависит от настроек CRM-трекера/линии; на Telegram не проверено | Включить штатное создание контакта на тестовой линии, получить обращение и повтор, проверить контакт и его связь с чатом. |
| Можно первым написать по любому известному телефону | API предусматривает PHONE; доступность произвольного получателя и ограничения не доказаны | Отправка на собственные доступный и недоступный тестовые аккаунты, фиксация безопасных кодов ошибок и ограничений edna. |
| Ответ по ID автоматически попадёт в исходный CRM-контакт | Главный риск этапа 3: телефон может отсутствовать | После исходящего по телефону получить ответ только с Telegram ID; проверить, даёт ли edna достоверную связку, затем фактическую CRM-привязку. |

До разработки основной цепочки закрыть первые три предпосылки. Последнюю исследовать в той же ранней пробе, даже если реализация CRM запланирована третьим этапом. Если подтверждённой связки нет, вариант штатной ручной привязки выносится владельцу как ограничение до приёмки этапа 3. Не разрабатывать эвристику по времени, имени или последнему номеру.

Для более точной оценки нужны три входа: фактические Telegram payload, результаты проверки CRM без телефона, подтверждённые ограничения/связка PHONE и TELEGRAM_ID. Сроки до этого не фиксируем как обязательство.

## 3. Срез локального кода и места изменения

Срез выполнен чтением исходников, без импорта `app.main`. Уже существующие незакоммиченные изменения сохраняются; перед реализацией понадобится сверка принятого образа с локальными исправлениями, чтобы не потерять промышленный install-fix и обработку ошибок webhook.

| Участок | Что сейчас | Планируемое изменение |
|---|---|---|
| `app/models.py` | Один `Portal.open_line_id`, один коннектор `max_bot`; старые MAX Bot без типа допустимы. `Message` хранит адрес и тип, но названия полей исторически MAX. | Сохранить общую линию и старые данные. Telegram получает явную адресацию и отдельное пространство личности; новые поля только если необходимы для устойчивого сопоставления. Не переименовывать исторические колонки ради нового канала. |
| `app/routers/api.py`, `settings_page.py` | Общая форма, профиль edna и webhook, управление каналами, выбор линии и тихая CRM-подготовка. | Добавить Telegram без повторной отрисовки/навязчивой синхронизации; правдивые состояния регистрации, активации и webhook; не показывать Telegram CRM до этапа 3. |
| `app/services/bitrix.py`, `app/routers/install.py` | `CONNECTOR_ID = max_bot` используется в регистрации, сообщениях и статусах. | Добавить явный выбор коннектора для новых Telegram-операций и восстановление его регистрации. Старые вызовы, идентификатор и настройки MAX не менять. |
| `app/routers/incoming.py` | Поиск типа идентификатора и имени ориентирован на MAX; при отсутствии типа используется MAX_ID. | Адаптер Telegram валидирует собственный контракт, отделяет ID edna от Telegram ID, не берёт имя из чужого мессенджера по совпавшим цифрам. |
| `app/routers/handler.py`, `app/services/delivery_worker.py` | В Открытых линиях ветка «не MAX Bot» вызывает MAX API; есть старые payload очереди. | Явная диспетчеризация Telegram/MAX/MAX Bot; старые payload читаются без изменения. Проверить CONNECTOR, LINE, портал и сохранённую связь чата до выбора отправителя. |
| `app/services/maxbot.py` | MAX и MAX Bot API, настройка callback, `VALID_ID_TYPES = MAX_ID, PHONE`. | Новый модуль `app/services/telegram.py` с собственным построением запросов; не расширять MAX-валидацию так, чтобы она принимала Telegram ID. Общие helpers выделять только при доказанно одинаковом контракте. |
| `app/routers/status.py` | Корреляция edna request с Открытой линией и CRM, статусы READ/ошибок. | Учесть Telegram-коннектор, ранние/поздние статусы и канал сообщения; не менять mapping статусов MAX. |
| `app/services/file_cache.py`, `routers/files.py` | Подписанный URL с TTL, содержимое в памяти. `handler.py` берёт первый файл. | Для Telegram решить сохранность медиа на всём сроке retry и при рестарте; определить обработку всех вложений и подписи. Удалять/переписывать кеш MAX ради Telegram не требуется. |
| `crm_channels.py`, `crm_providers.py`, `crm_outreach.py`, `crm_worker.py` | Таблица возможностей содержит только MAX; приём и worker дополнительно жёстко проверяют MAX. | В этапе 3 расширить все проверки согласованно; одной записи в CAPABILITIES недостаточно. Сохранить provider CODE MAX и их обработчик. |

Техническое предложение: отдельный коннектор Telegram, например `edna_telegram`, **на той же общей линии**. Это не отдельная линия и не новое приложение. Он позволит различать источник и не менять регистрацию `max_bot`. До закрепления ID проверить два Telegram-отправителя на одной линии, группировку диалогов (`CHAT_GROUP`) и отсутствие влияния на контакты MAX. Отдельный коннектор не заменяет проверку маршрутизации каждого события.

## 4. Этап 1: подключение, текст, контакт

Требования: TG-01–TG-08 и TG-SAFE-01–06.

### 1А. Проверка контракта на тестовом отправителе

1. Подтвердить доступный в edna Telegram-канал и точное значение его `type`. Сохранить обезличенные fixtures без API-ключа, телефонов и токенов URL.
2. Зафиксировать фактические схемы входящих/статусов, типы `subscriber.identifier` и `subscriber.identifiers`, значение `subscriber.id`, имя и поля принадлежности каналу. Отсутствие Telegram в общей справке не заполнять догадками.
3. Проверить настройку callback строго для выбранного subjectId: текущий код использует singular-поля, новая справка показывает и array-поля. Выбрать подтверждённый контракт Telegram, не менять работающий MAX автоматически и не вызывать настройку без ограничения каналом.
4. Получить текст от клиента без телефона, ответить по достоверному Telegram ID. Проверить максимальный текст, Unicode/эмодзи, блокировку/недоступность получателя, фактические статусы и ключ корреляции `outMessageId`/status. Лимит 4000 из MAX не переносить без проверки.
5. На тестовой линии подтвердить создание именно контакта без номера и отсутствие нового контакта при повторе. Отдельно проверить ответ после исходящего по телефону для будущего этапа 3.

Результат 1А: описанный контракт и набор безопасных fixtures, таблица ограничений, решения по идентичности и статусам. Если входящие Telegram недоступны, основной этап не объявляется реализуемым только по странице отправки; требуется ответ edna. Здесь планируем проверку, реальные настройки в текущей задаче не меняем.

### 1Б. Реализация

1. Ввести внутренний флаг Telegram, по умолчанию выключенный. Зарегистрировать Telegram-коннектор при включённой функции, активировать на `Portal.open_line_id`; сохранить восстановление после штатного обновления/открытия настроек без снятия активации MAX.
2. Добавить адаптер текста Telegram и явную таблицу поддерживаемых типов. Сохранить legacy `None → MAX_BOT`; неизвестные новые типы не направлять в MAX. Ошибка Telegram не меняет транспорт MAX.
3. Добавить отдельное пространство `user.id` для Telegram и устойчивый `chat.id`, различающий Telegram-отправителей. Конкретный формат закрепить после 1А; проверить ограничение/группировку в Bitrix. Существующие MAX/MAX Bot ID не пересобирать. Числовые ID хранить строками, не пропускать через JavaScript Number.
4. Связь для ответа хранить с порталом, каналом/устойчивой подписью, Telegram-адресом и его типом, коннектором и линией. Отсутствующий/противоречивый тип не заменять MAX_ID. Текущий `subscriber.id` edna не использовать как Telegram ID без подтверждения.
5. Передавать в Битрикс только имеющиеся имя/phone; CRM-трекер не отключать. Не добавлять `crm.contact.add` или новые CRM-права для дублирования штатного создания. Если для достоверной привязки понадобится дополнительный scope, вынести решение отдельно.
6. Входящие и исходящие сохранять с задачей до подтверждения приёма. Для Telegram-ответа предусмотреть устойчивый ID операции, дедупликацию, конечные ошибки и неопределённый исход после отправки. Политику безопасных повторов Telegram не выводить из одного наличия поля outMessageId.
7. Статусы и ошибки показывать в том же Telegram-диалоге; служебное уведомление не должно повторно уходить клиенту. Сохранять фактическую линию исходящего для поздних статусов, а не подставлять новую общую линию.
8. Сохранить текущие правила управления каналами, скрытие ключей и тихое открытие формы. При отключении одного Telegram-канала не отключать общий коннектор при наличии остальных активных каналов этого типа и не деактивировать MAX.

### Приёмка этапа 1

- Новый/повторный клиент, только Telegram ID, отсутствующее имя, имя изменилось, закрытый и повторно открытый диалог.
- Два Telegram-отправителя на одной линии; одинаковые числовые MAX/Telegram ID; два портала. Нет смешения адресатов/имён/контактов.
- Подключение, постоянная/временная ошибка callback, переименование, отключение и повторное подключение, смена общей линии с сохранением старых статусов.
- Повтор входящего и события оператора, параллельная обработка, early status, потеря ответа, остановка и восстановление worker.
- Реальный контакт без телефона и оператор без административных прав; неверные токены не вызывают отправку.
- Регрессия MAX, MAX Bot, MAX из CRM с Telegram выключенным и включённым.

Этап 1 не принимается без фактического входящего текста, ответа на устройстве клиента и проверки контакта в CRM. При неподтверждённом READ метка не показывается, ограничение фиксируется.

## 5. Этап 2: вложения и геолокация

Требования: TG-09–TG-13, те же требования безопасности и очереди. До реализации собрать входящие образцы и заполнить матрицу ниже; сейчас «проверить» означает незакрытую проверку, а не поддержку.

| Вид | Клиент → Открытая линия | Открытая линия → клиент |
|---|---|---|
| Изображение | Проверить реальный payload, файл и подпись | IMAGE; проверить скачивание/отображение и подпись. |
| Документ / произвольный файл | Проверить MIME/имя, отображение и загрузку | DOCUMENT; файл без молчаливой потери имени/текста. |
| Видео | Проверить обычное видео и видеофайл отдельно | VIDEO либо согласованный файл при ограничении формата. |
| Аудиофайл | Проверить воспроизведение/скачивание | AUDIO; поддерживаемые контейнеры и лимиты подтвердить. |
| Голосовое сообщение | Проверить отдельный тип/контейнер edna и воспроизведение | Нативный voice не подтверждён; допустимый базовый результат – аудиофайл, ограничение показать. |
| Геолокация | Точка → текст + ссылка на карту | Нативная LOCATION только при получении координат из UI; иначе обычная текстовая ссылка. |
| Стикер, анимация, кружок, контакт, альбом и иной тип | Проверенный файл/текст либо видимое предупреждение | Не обещать нативный тип без контракта и UI; неподдерживаемое отклоняется понятно. |

Порядок работ:

1. Адаптер входящих вложений, подписей, нескольких файлов, неизвестного/пустого контента. Проверка MIME/содержимого, безопасных имён, URL, размера и координат. Не терять остальную часть сообщения из-за одного недоступного вложения без уведомления.
2. Адаптер исходящих вложений. В документации отправки Telegram поле caption не описано: сначала проверить поддержку; если её нет, согласовать текст отдельным сообщением с собственной дедупликацией и порядком. Не копировать MAX-caption молча.
3. Получать файл Bitrix до истечения SIGN. Для новых Telegram-задач обеспечить доступное всем worker защищённое хранилище/постоянный ключ на срок доставки; один кеш памяти с TTL 10 минут не покрывает существующий retry до 30 минут и рестарт. Новая реализация не должна менять ссылки/кеш незавершённых MAX-задач.
4. Ограничить скачивание доверенными HTTPS-источниками, включая проверку redirect, внутренних IP/DNS и размера потока; не считать переданный пользователем MIME доказательством безопасности. Скрывать подписи/токены URL в диагностике.
5. Срок хранения и очистку связать с состоянием задачи и временем скачивания edna. Перевыпуск подписанного URL не продлевает публичный доступ навсегда. Недоступный после принятия файл – восстановление либо видимая конечная ошибка.

Приёмка: каждый тип в обе стороны, с подписью/без, больше одного файла, границы размера/формата, просроченный URL, небезопасный redirect, обрыв загрузки, delayed worker и рестарт. Фактическое отображение voice/видео/геолокации записать отдельно от успешного HTTP. Выполнить регрессию вложений MAX/MAX Bot.

## 6. Этап 3: текст из карточки контакта по телефону

Требования: TG-14–TG-18. Текстовый адаптер этапа 1 переиспользуется; медиа этапа 2 не является технической зависимостью CRM-текста, но порядок поставок сохраняем по предложению владельца.

1. Расширить явные возможности в `crm_channels.py`: отдельный префикс провайдера, например `edna_telegram_<channel.id>`, подпись Telegram от edna, PHONE и TEXT. Коды `edna_max_*`, их NAME/HANDLER и персональные настройки не сбрасывать.
2. Согласованно обновить регистрацию/reconcile, приём callback и worker: убрать жёсткие MAX-проверки только в пользу явной проверки поддерживаемой возможности, а не разрешения всех типов. Добавить отдельный внутренний контроль CRM Telegram, по умолчанию выключенный, независимо от CRM MAX.
3. Переиспользовать проверенную авторизацию: контекст приложения, ожидаемый CODE, application_token, портал + provider + канал, активность и scope. `imopenlines` для этапов 1–2, уже используемый `messageservice` для этапа 3. Новые scopes по умолчанию не добавлять. Установка без messageservice продолжает принимать Telegram в Открытой линии.
4. Сохранить существующую атомарность `CrmOutgoingMessage + MessageDeliveryTask`, уникальные ключи по порталу/provider/message_id, PHONE-нормализацию и bindings. Типичные ошибки телефона и лимита текста обрабатывать до сетевой отправки; лимит Telegram подтверждается отдельно от MAX.
5. Отправлять через Telegram-адаптер с сохранённым outMessageId. Подтвердить фактическую семантику повторного ID; после тайм-аута возможного принятия использовать uncertain/сверку, а не генерировать новый ID и посылать ещё раз. Неуспех обновления статуса CRM не повторяет отправку клиенту.
6. Обработать ранние/поздние/повторные статусы без регресса состояния. Реальные Telegram-статусы сопоставить с текущими queued/sent/delivered/undelivered/failed; отдельного стандартного read нет. Не копировать правило «Просмотрено» Открытой линии в CRM.
7. Ответ клиента пропускать по Telegram-входящему маршруту этапа 1. Сопоставлять с CRM по достоверным данным edna/платформы. При отсутствии телефона проверить поддерживаемый способ связи, не создавать фиктивный входящий и не считать сходство ID доказательством. Автоматический перенос первого исходящего текста в историю линии остаётся вне этой задачи.
8. Сохранить автоматическое обновление имени/удаление отправителя при отключении и проверку активности при отправке из устаревшего UI. Уже принятые статусы не терять после выключения Telegram CRM.

Приёмка: контакт с одним/несколькими/отсутствующим телефоном, новый и известный получатель, доступный/недоступный Telegram, два отправителя и два портала, оператор без админских прав, повтор callback/статуса, гонка отключения, неопределённый исход. Обязательно проверить ответ только с Telegram ID и реальную привязку к карточке; нерешённый случай не скрывать за успешной отправкой. Отдельно подтвердить, что CRM MAX остался работоспособен.

## 7. Общая проверка совместимости и выпуска

Перед началом реализации зафиксировать выбранные файлы локальных исправлений и фактический принятый промышленный артефакт. Не заменять рабочую папку GitHub-версией и не включать все текущие правки в будущий коммит автоматически.

| Область | Что проверяем на каждом этапе |
|---|---|
| Старая схема и очередь | Старые строки с NULL type, старые payload, повторный запуск миграции и сохранение истории. Добавочные изменения испытываются в отдельной БД до запуска общего worker. |
| MAX Bot | Старые голые ID, входящий/ответ/вложения, прежний выбор канала, отсутствие выдуманного READ. |
| MAX | Помеченные chat.id, имя клиента, входящий/ответ/вложения, реальные статусы. |
| CRM MAX | Старые provider CODE, отправка PHONE, статусы, uncertain, переименование/отключение, отсутствие лишних синхронизаций. |
| Авторизация | Установка/обновление версии, административные проверки, отклонение чужого портала/токена, обычный оператор, прежние scopes. |
| Telegram выключен | Нет регистрации отправителей/новых отправок Telegram; MAX и существующие задачи не затронуты. Поздние статусы уже принятых Telegram-сообщений сохраняются. |
| Частичный сбой | Неактивная линия, отозванный ключ, 429/5xx, БД недоступна, конкурентные worker, early/late status и рестарт. Ошибка одного канала не останавливает остальные. |

Автоматические проверки планируются по смыслу: адаптеры контрактов и ошибок, изоляция/маршрутизация, дедупликация и переходы состояний, миграция на PostgreSQL, текущий изолированный Python-прогон и Node-проверки формы. Синтаксис проверять разбором исходников; `app.main` не импортировать для пассивной проверки. Живые отправки и изменение webhook выполняются в согласованном тестовом окружении, не на каналах действующих клиентов.

Для каждого этапа сохранять версию кода/образа, выполненные проверки, наблюдения на устройствах и остаточные ограничения. Включать сначала на выбранном тестовом портале, затем после приёмки готовить пакет для edna. Не приравнивать push к успешной сборке/выкладке. Обновить DevOps-инструкцию только параметрами и миграциями готового этапа.

Остановка новых Telegram-отправок выполняется отдельным контролем, без выключения CRM MAX, потери истории и обработки статусов. Автоматический откат на старый образ не планируется: сначала проверить совместимость схемы и новых типов задач; для промышленной миграции соблюдать штатную резервную копию/процедуру edna. Сбои Telegram не требуют удаления приложения и переподключения MAX/MAX Bot.
