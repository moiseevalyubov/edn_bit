Миграция добавляет таблицы/поля и сохраняет старые строки; не запускать отдельные DDL вручную параллельно со стартом.
3. Определить **ожидаемый CODE именно этого приложения** по app.info с доверенной административной авторизацией и задать BITRIX_EXPECTED_APP_CODE. Это не имя `bitrix-dev` в интерфейсе и не хеш сборки. Значение стенда пока не установлено. Не угадывать его по OAuth client_id. Проверить APP_BASE_URL с актуальным доменом msk1, без секретов в URL.
4. Проверить наличие сохранённого application_token и действующего административного OAuth этой установки, не показывая значения. При отсутствии токена восстановить доверенную установку/обновление приложения; не принимать токен из первого произвольного callback и не копировать токен сотрудника в серверные настройки.
5. Убедиться, что приложению и сохранённому OAuth выдан messageservice: scope без full=true. Сохранить прежний imopenlines. Если нужно новое разрешение для опубликованной версии, подтвердить обычный процесс обновления приложения администратором; пользователи не создают вебхуки и не вводят коды регистрации.

Изолированные проверки разработчика: `.venv\Scripts\python.exe -X utf8 tests/run_isolated.py`, `node tests/check_crm_ui.js`. ## Один канал и один согласованный получатель

1. После подтверждения предыдущих условий включить CRM_OUTREACH_ENABLED на **стенде**. Открыть существующую форму приложения администратором. Она сама проверит приложение/права, включит портал и запланирует provider для активного MAX. На стенде ожидается существующий канал 9 и CODE `edna_max_9`; это исторические сведения, проверить их перед приёмкой.
2. Дождаться завершения сообщения «Обновляем каналы…». В реестре должен остаться один CODE канала; sender.update заменяет HANDLER пробы на `/crm/messages/send` и устанавливает имя `MAX от edna — <название канала>`. Дополнительного переключателя/регистрационного URL в форме нет. Проверить переименование в форме и тот же CODE после него.
3. Открыть карточку тестового контакта/сделки **обычным сотрудником**, имеющим необходимые права CRM. Проверить выбор нашего отправителя. Надписи SMS допустимы по согласованию: выбранный messageservice поддерживает TYPE=SMS. Внешний запрос при этом идёт только в MAX, SMS API не вызывается.
4. Отправить ровно один согласованный текст на согласованный тестовый номер в международном формате. У получателя может не быть доступности по телефону в MAX; отказ edna нужно отобразить честно, а не ставить delivered. Не начинать с реального клиента и не делать массовую отправку.
5. Сверить одну запись CRM-message ID, один outMessageId, один HTTP POST в edna и фактический текст на стороне MAX. Сохранить время в МСК. HTTP 200 edna означает accepted; sent/delivered берутся из событий. READ сохраняется у нас и подтверждает delivered в CRM — отдельную надпись «прочитано» этот REST-метод не даёт.
6. При ошибке проверить событие/текст/статус в CRM и реакцию формы. Полный контракт ошибок callback пока подтверждён только заглушками и старой пробой успеха; результат ordinary user и ошибки UI зафиксировать отдельно. Повтор одного callback не должен создавать второе сообщение. Не имитировать сетевой timeout повторной отправкой реальному человеку.
7. Попросить тестового получателя ответить. Проверить прежний входящий путь, контакт CRM, правильный канал и Открытую линию. Исходящее сообщение из CRM пока не переносится в историю новой Открытой линии автоматически; это условное исследование CRM-MAX-09. Новая линия создаётся после ответа клиента по принятому сценарию.

## Несколько каналов, отключение и сбои

- Подключить второй тестовый MAX через ту же форму. У каждого должен быть свой CODE/NAME и свой sender в edna. Проверить отправку/ответ по каждому; MAX_BOT и неподдерживаемые типы не появляются как новые MAX-отправители.
- Отключить тестовый канал. Он должен исчезнуть из выбора CRM после фоновой синхронизации; до её завершения старый видимый пункт уже не должен отправлять. Queued отменяются с failed, начатый HTTP нельзя гарантированно отозвать. После отключения известные статусы продолжают сохраняться.
- Отдельно установить, принимает ли Битрикс24 status.update старого сообщения **после sender.delete**. Если нет, зафиксировать ограничение показа в CRM: локальный факт остаётся; отключённый provider ради статуса не регистрируется заново. Пока это не подтверждено реальным порталом.
- При uncertain администратор видит канал, время, CRM ID и outMessageId в форме. Передать эти ID поддержке edna для сверки. Не помечать результат «не доставлено» и не нажимать «отправить ещё раз», пока исход неизвестен. Документация истории edna ещё не подтверждает поиск MAX по собственному outMessageId.
- Проверить восстановление синхронизации после краткого отказа API и повторного открытия формы. При удалении приложения новые отправки прекращаются, queued отменяются, старый OAuth больше не используется. Поведение удаления отправителей самой платформой требует практической проверки. После проверенной переустановки форма снова подтверждает контекст и scope; не включать портал без этих проверок.

Для разбора теста передать время МСК, снимок CRM с событием/статусом, ID CRM и outMessageId, строки `CRM message … received`, `CRM send task … completed`, `CRM status … recorded` и ошибки `CRM provider … sync failed`/`CRM status task …`. Обычные HTTP-логи полезны только вместе с ID. Не передавать auth, .env, API-ключ, Authorization, полный секретный webhook URL и ненужные телефоны/тексты клиентов.

## Остановка и откат

Предпочтительная остановка — CRM_OUTREACH_ENABLED=0 **при сохранении совместимого нового worker и BITRIX_EXPECTED_APP_CODE**. Новые callback не принимаются для отправки, send-задачи не выбираются; локальная сверка (до 60 секунд) отменяет queued и планирует удаление отправителей. Статусы уже переданных запросов остаются отдельными задачами. Проверить результат удаления и наличие uncertain; не считать переключение флага доказательством отмены уже начатого HTTP.

Не возвращать вслепую старый worker из 770f5af: он не знает новые task_type. Для отката к старому образу сначала нужен отдельный проверенный порядок завершения/изоляции новых операций. Не удалять новые таблицы/поля и не очищать очередь/историю ради отката. Возможность выбора старого образа в интерфейсе Amvera и процедура восстановления БД должны быть подтверждены заранее; наличие кнопки отката не предполагается. Состояние прежней интеграции проверить отдельно.

Условные возможности CRM-MAX-02 (иконка), CRM-MAX-06 (отдельное прочтение) и CRM-MAX-09 (история в Открытой линии) не включать в обещания до практического исследования. Промышленный выпуск — после приёмки обязательных сценариев и отдельного плана обновления установок.
