# Релиз #22: инструкция обновления для DevOps

**Текущий план обновления 15 существующих клиентов:** messageservice вводится впервые, прежнее право imopenlines сохраняется. Владелец допускает однократное открытие формы администратором клиента, поэтому отдельная массовая/постоянная фоновая подготовка для этого релиза не требуется. После получения новых прав существующая `/api/crm/prepare` проверяет контекст, выданный scope, сохранённую административную авторизацию и application_token и планирует отправителей уже активных MAX-каналов. Этот механизм проверен на тестовой установке; каналы повторно подключать не требуется.

**Оставшийся вопрос выпуска:** подтвердить переход существующей опубликованной установки с одним imopenlines на imopenlines + messageservice. Открытие формы само по себе не выдаёт отсутствующее право. На контрольной установке проверить штатное обновление/подтверждение прав Битрикс24, действующий scope не только браузерного, но и сохранённого серверного OAuth, затем открытие формы администратором и контрольную отправку. Сценарий расширения прав опубликованной версии ещё не пройден; конкретный экран подтверждения не установлен. Не удалять и не переустанавливать клиентское приложение ради проверки. Инструкция для клиента: [CRM_OUTREACH_CLIENT_UPDATE.md](CRM_OUTREACH_CLIENT_UPDATE.md).

Серверная выкладка и обновление версии в Маркете являются разными этапами. Изменения карточки опубликованного приложения подлежат модерации; готовность к серверной выкладке не гарантирует доступность обновления прав всем клиентам в тот же день. Основание: [официальный FAQ публикации](https://github.com/bitrix24/b24restdocs/blob/main/market/preparing-to-publish/faq.md). Не выбирать другой минимальный тариф автоматически: на присланном экране указан Базовый, фактическую доступность messageservice проверить на контрольной установке.

## Обязательная новая настройка: BITRIX_EXPECTED_APP_CODE

**Для включения функции в промышленном окружении DevOps обязан задать `BITRIX_EXPECTED_APP_CODE`. Это постоянная настройка безопасности, а не временная переменная для теста.**

Сервер сравнивает её значение с `CODE`, который Битрикс24 возвращает методом `app.info`, и проверяет, что авторизация относится к нужному установленному приложению. Пустое или неверное значение блокирует подготовку функции и управление каналами при её включении. Успешный запуск процесса или ответ `/health` не заменяет эту проверку.

- Настройку задаёт команда edna один раз для серверного окружения приложения; на всех его репликах значение должно совпадать.
- Клиенты приложения **не добавляют эту переменную у себя**, не вводят CODE и не создают отдельные вебхуки/регистрации каналов.
- Значение — `result.CODE` из `app.info` **промышленного приложения**, проверенный в его OAuth-контексте. Это не отображаемое имя приложения и не значение, угаданное по `BITRIX_CLIENT_ID`.
- На текущем предпроде через `app.info` подтверждено `edna.bitrix_plugin_edna_ru`. Для промышленного окружения значение нужно проверить отдельно, даже если ожидается то же самое. Не копировать стендовое значение без проверки.
- CODE не является секретом: допустима обычная переменная окружения. OAuth-токены, Client Secret и application_token при получении CODE не выводить и в этот документ не добавлять.
- После выпуска переменную сохранять в конфигурации окружения. Если портал уже использовал функцию, административное управление остаётся защищённым и при глобальном выключении отправки.

Метод и поле проверены через b24-dev-mcp. [Документация app.info](https://apidocs.bitrix24.ru/api-reference/common/system/app-info.html). Проверка в коде: [crm_auth.py](../app/services/crm_auth.py).

## Новые параметры релиза

| Переменная | Значение и назначение |
|---|---|
| `BITRIX_EXPECTED_APP_CODE` | Обязательна для включения новой функции; точный CODE приложения соответствующего окружения. Постоянная настройка. |
| `CRM_OUTREACH_ENABLED` | Сначала `0`, после подготовки и проверки окружения — `1`. По умолчанию функция выключена. Это серверное управление выпуском, не пользовательский переключатель. |
| `PROBE_22` | `0` в промышленном окружении и при проверке настоящей отправки. Временная проба не отправляет в MAX и имитирует delivered; использовать её как рабочую функцию нельзя. |

При `CRM_OUTREACH_ENABLED=0` прежняя интеграция Открытых линий запускается без нового CODE. Это позволяет сначала установить совместимый код с выключенной функцией. Для последующего включения `BITRIX_EXPECTED_APP_CODE` необходим.

## Порядок обновления

1. Зафиксировать итоговый коммит/образ релиза и последнюю рабочую версию. Для промышленной БД подтвердить резервную копию и порядок восстановления. Существующие `SECRET_KEY`, данные каналов и OAuth сохранить; смена ключа шифрования не входит в этот релиз.
2. Получить и проверить CODE промышленного приложения, добавить `BITRIX_EXPECTED_APP_CODE` в конфигурацию всех реплик. Установить `CRM_OUTREACH_ENABLED=0`, `PROBE_22=0`.
3. Подтвердить у приложения разрешение `messageservice`, сохранив прежний `imopenlines`. Проверять фактически выданные права через `scope` без `full=true`. Если требуется обновление разрешений опубликованного приложения, подготовить обычный процесс подтверждения администратором установки; технических настроек от каждого клиента не требуется.
4. Проверить наличие доверенного сохранённого application_token и действующего административного OAuth. Токен сотрудника из события/браузера не заменяет серверные административные учётные данные. При отсутствии нужной авторизации восстановить её штатным проверенным способом; проверки кода и прав не отключать.
5. Развернуть код сначала с выключенной отправкой. Добавочные миграции применяются при старте; новые таблицы/поля не заменяют старые данные. Проверить запуск, `/health`, прежние входящие/исходящие Открытых линий и журнал миграции.
6. Включить `CRM_OUTREACH_ENABLED=1` и применить переменные к работающим процессам. В Amvera для применения переменных нужен перезапуск контейнеров; одна запись в форме не считается подтверждением применения. [Документация Amvera](https://docs.amvera.ru/applications/configuration/variables.html).
7. Открыть форму приложения администратором на контрольной установке. Сервер сам проверит CODE, права, scope, сохранённые токены и запланирует отправителей активных MAX. Нормальная синхронизация выполняется в фоне без информационной плашки; после сохранения канала держать форму открытой не требуется. Если показано предупреждение о контексте/авторизации, устранить причину до теста. Через несколько секунд заново открыть CRM и проверить наличие отправителей.
8. Выполнить приёмку по [CRM_OUTREACH_ACCEPTANCE.md](CRM_OUTREACH_ACCEPTANCE.md): один тестовый получатель, реальное получение текста в MAX, настоящие статусы, ответ клиента, переименование/несколько каналов/отключение. Только после приёмки считать функцию выпущенной. Отдельное прочтение и перенос исходящей истории в Открытую линию не обещать без проверки.

## Результаты приёмки и ограничения на 06.11.2026

После прямой доставки в Amvera (merge f4af2c6, исходный GitHub 5e16211) пользователь подтвердил успешное обновление и принял оба исправления: новый формат имени отправителя и замену описания «Проба #22». Пункты 1–2 завершающей визуальной проверки ниже выполнены. Это не закрывает блокирующий вопрос автоматической подготовки существующих установок, указанный в начале документа.

На предпроде пользователь подтвердил: настоящая отправка из CRM в MAX; сохранение текста в карточке нужной сделки; READ и отображение delivered в CRM; ответ клиента в Открытой линии; ответ оператора в MAX; переименование; два независимых отправителя; отключение одного канала с исчезновением его отправителя; повторное подключение с новым уникальным именем и последующую доставку сообщения. Проверено открытие ссылки на файл у получателя. Это текст со ссылкой, а не отправка нативного файлового вложения из CRM.

Ограничения выпуска:

- Отправка выполнялась администратором. Отдельной учётной записи обычного сотрудника на предпроде нет. До включения функции для клиентов проверить одну отправку сотрудником с доступом к нужной CRM-карточке без прав администратора; регистрацию отправителей заранее выполняет форма приложения в административном контексте.
- Штатный интерфейс messageservice использует SMS-надписи, включая «доставлено». Реальный READ хранится приложением, но отдельного read у messageservice нет. Это согласованное ограничение.
- Исходящее CRM-сообщение видно в карточке CRM, но не копируется автоматически в переписку Открытой линии. Условная возможность отложена, не обещать её в релизе.
- Исходящие из CRM поддерживают текст, включая вставленные Битриксом ссылки. Нативные вложения этого сценария не реализованы. Доступность конкретной ссылки зависит от настроек доступа к файлу; успешная проверка одного файла не гарантирует доступ ко всем.
- Название приложения над редактором берётся из установленного приложения Битрикс24. Перед промышленным выпуском проверить опубликованное название; стендовое bitrix-dev не является заданным кодом названием промышленного приложения.

Изолированная проверка после исправления описания отправителя: 78 найденных тестов, 67 выполнены успешно, 11 PostgreSQL пропущены (отдельная тестовая БД не запущена). Проверены повтор callback без повторной отправки, конфликтующие повторы, реальные READ и запоздалые статусы, неопределённый результат timeout без слепого повтора, явный отказ edna, повтор обновления статуса без повторной отправки, восстановление синхронизации провайдера, замена описания старой пробы. Ранее перед основной выкладкой отдельно пройдены все 78, включая PostgreSQL. Изолированные проверки используют синтетические данные и подменённый HTTP; реальные отказы edna и гонки на предпроде ими не воспроизводились.

Обязательная завершающая проверка после доставки исправлений на предпрод:

1. Подтвердить новую сборку, затем открыть форму приложения администратором и дождаться синхронизации. Формат имени отправителя должен быть `<имя канала> в приложении MAX от edna`; с префиксом CRM получается «Отправим сообщение с номера <имя канала> в приложении MAX от edna».
2. Раскрыть выбор отправителя: вместо старого «Проба #22» должно быть рабочее описание «Отправка сообщений из CRM через edna». Каналы повторно не подключать.
3. Выполнить одну контрольную отправку на собственный тестовый номер и сверить реальное получение, отсутствие дубля и статус. Зафиксировать итоговый коммит релиза. До этой проверки оба исправления не считать принятыми пользователем.

Изменение формы после замечаний владельца: готовые неизменившиеся отправители при открытии формы не синхронизируются принудительно; новые/изменённые создают фоновые задачи. Автоматические повторы временных ошибок сохраняют свою задержку. Повторное открытие позволяет восстановить окончательно завершившуюся ошибкой синхронизацию после устранения причины. Успешная синхронизация не показывает информационных уведомлений; предупреждения о реальных ошибках и неопределённой отправке сохранены. Первоначальный список каналов отображается один раз после проверки доступа, без промежуточного списка без кнопок. Кнопка переименования остаётся в единой раскладке, но недоступна без подтверждённых прав; для установок версии 1 не включается messageservice и не обходятся проверки безопасности.

Проверки совместимости формы: установка только с imopenlines и без application_token сохраняет подключение, переименование администратором и отключение каналов без вызовов messageservice; при глобально выключенной функции прежние endpoints списка/отключения и prepare работают без нового CODE и без новой авторизации. Отдельные проверки UI подтверждают показ формы при выключенной функции или ошибке CRM-подготовки. Это изолированные тесты; реальная приёмка обычным сотрудником остаётся отдельным пунктом.

## Порядок остановки

Для остановки задать `CRM_OUTREACH_ENABLED=0`, сохранив `BITRIX_EXPECTED_APP_CODE` и совместимый новый worker. Сверка отменит ещё не начатые сообщения и запланирует удаление отправителей; начавшуюся внешнюю отправку нельзя гарантированно отозвать. Обработка статусов уже переданных сообщений продолжается.

Не откатывать вслепую к worker из `770f5af`: он не знает новые типы задач. Не удалять добавленные таблицы/поля и не очищать очередь ради отката. Подробный порядок и открытые вопросы платформы — в [инструкции приёмки](CRM_OUTREACH_ACCEPTANCE.md).
