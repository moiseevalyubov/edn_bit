# PRD: Приложение интеграции MAX-бот с Открытыми линиями Битрикс24

## 1. Overview

### Что это
Приложение для маркетплейса Битрикс24, которое подключает канал MAX-бот к Открытым линиям. Позволяет операторам принимать и отправлять сообщения (текст, изображения, файлы, видео, аудио) абонентам MAX-бот прямо из интерфейса Битрикс24.

### Зачем это нужно
Компании, которые используют Битрикс24 как CRM и MAX-бот как канал коммуникации, вынуждены работать в двух разных интерфейсах. Это приводит к потере обращений, медленным ответам и невозможности инициировать диалоги с клиентами из CRM.

### Архитектура
- Уже существует сервер, подключённый к MAX-бот, с API для отправки сообщений и вебхуком для получения входящих сообщений
- Приложение Битрикс24 выступает посредником: принимает входящие с сервера и передаёт в Открытые линии, а исходящие от операторов — обратно на сервер
- Сообщения не отправляются синхронно — они помещаются в персистентную очередь (`message_delivery_tasks` в БД), фоновый worker доставляет их с автоматическим retry при временных сбоях

## 2. Целевой сегмент

### Кто эти люди
Малый и средний бизнес с активными продажами через мессенджеры. Менеджеры по продажам и руководители отделов продаж в компаниях, которые уже используют Битрикс24 на платном тарифе и MAX-бот как канал коммуникации с клиентами.

### Big Job
Не терять ни одного обращения клиента и конвертировать больше диалогов в продажи, чтобы растить выручку без увеличения рекламного бюджета.

### Core Jobs

**Core Job 1: Быстрый ответ клиенту из CRM**
- **Когда** клиент пишет в MAX-бот с вопросом о товаре/услуге, **хочу** быстро ответить ему прямо из Открытых линий Битрикс24, не переключаясь между окнами
- **Критерии успеха:** сообщение от клиента появляется в Открытых линиях; оператор отвечает в том же окне; ответ доставляется клиенту в MAX-бот

**Core Job 2: Инициация диалога с клиентом**
- **Когда** клиент давно не покупал, **хочу** написать ему первым в мессенджер через Открытые линии с персональным предложением
- **Критерии успеха:** возможность начать диалог с абонентом, который ранее уже писал в MAX-бот

## 3. Scope MVP

### Что входит в MVP

#### 4.1. Подключение канала MAX-бот
- Веб-форма с 3 текстовыми полями:
  - **Название канала** — произвольное имя для идентификации
  - **API-ключ** — ключ для обращения к серверу MAX-бот
  - **Sender** — идентификатор приложения MAX-бот
- Один портал Битрикс24 может подключить несколько каналов MAX-бот
- **Sender ID уникален среди активных каналов портала.** Нельзя подключить тот же MAX Bot канал повторно, пока первый активен. После отключения канала Sender ID освобождается.
- **Название уникально среди всех каналов портала** (активных и отключённых), без учёта регистра. Это исключает путаницу в истории каналов.
- **Sender ID должен совпадать с названием подписи (`subject`) канала в личном кабинете edna** — по нему приложение находит канал в edna при автонастройке (см. ниже)
- Фиксируется дата/время каждого подключения и отключения канала
- Во время подключения показывается индикатор загрузки («Подключение…») — процесс может занять несколько секунд, т.к. приложение обращается к API edna
- Канал можно отключить после сохранения: при отключении канал не удаляется из БД, а помечается как отключённый; фиксируется дата/время отключения
- Список каналов отображает 3 последних (по дате подключения). Если каналов больше — остальные скрыты; под таблицей появляется кнопка «Все каналы (N)», раскрывающая полный список. Колонка **«Тип канала»** показывает тип из edna (например `WHATSAPP`); у каналов, подключённых до внедрения автонастройки, стоит «—»
- При любых ошибках показывается сообщение об ошибке от бэкенда как есть, без изменений

##### Автоматическая настройка webhook (callback URL) в edna

При нажатии «Подключить» приложение само прописывает адрес для входящих сообщений в edna — копировать URL вручную больше не нужно. Автонастройка выполняется **до** создания канала, двумя запросами к API edna (заголовок `X-API-KEY` с введённым ключом):

1. `GET https://app.edna.ru/api/channel-profile` — получить список каналов; найти тот, у которого `subject` совпадает с введённым Sender ID; взять `subjectId` и `type`.
2. `POST https://app.edna.ru/api/callback/set` — передать `subjectId` и `inMessageCallbackUrl` (наш адрес `/incoming/{token}`). Успех — ответ `code == "ok"`. edna при сохранении проверяет доступность URL (ждёт `200 OK` на GET/HEAD).

**Бизнес-правила (валидность канала проверяется ДО его создания):**

Принцип: *если канал нельзя получить и проверить в edna — создавать его нельзя.*

- **Успех** → канал создаётся, webhook прописан автоматически. URL пользователю не показывается (всё уже настроено), в списке заполняется «Тип канала». В БД сохраняются `subjectId` и `type` канала.

- **Канал НЕ создаётся** (заведомо нерабочий или непроверяемый) → показывается ошибка, поля формы сохраняются для исправления:
  - **Sender ID не найден в edna** (нет канала с таким `subject`) — «В edna не найден канал с таким Sender ID. Проверьте, что Sender ID точно совпадает с названием подписи (subject) в личном кабинете edna.»
  - **Ключ невалиден** (edna ответила `401`) — «edna не приняла API-ключ (401). Проверьте, что ключ верный и активен.»
  - **У ключа нет доступа к подписи** (edna ответила `403`) — «у API-ключа нет доступа к этой подписи (403). Проверьте разрешения этого ключа в edna или правильность названия подписи (Sender ID).» (при 403 список каналов не приходит, и существование подписи проверить нельзя)
  - **Канал не активирован** в edna (нет `subjectId`) — «Канал найден в edna, но ещё не активирован… Активируйте канал в edna и подключите его снова.»
  - **edna не знает subjectId** при установке URL (`error-subject-unknown`).

- **Канал создаётся, но webhook нужно указать вручную** (временный сбой, конфиг скорее всего верный) → показывается причина + webhook URL с кнопкой «Скопировать»; пользователь прописывает его в edna сам (как раньше):
  - сеть/прокси до edna недоступны, edna вернула `5xx`, либо edna не смогла проверить наш URL из-за «холодного старта» хостинга (Render «засыпает» при простое).
  - Это страховка на случай недоступности автонастройки — канал остаётся рабочим, обмен сообщениями возможен после ручной настройки URL.

#### 4.2. Приём входящих сообщений
- Приложение принимает вебхуки от сервера MAX-бот с входящими сообщениями
- Поддерживаются типы контента: **TEXT**, **IMAGE**, **DOCUMENT**, **AUDIO**, **VIDEO**, **VOICE**, **LOCATION**
  - Изображения — приходят как `IMAGE` (`.webp`)
  - Голосовые сообщения — приходят как `AUDIO` (`.mpga`)
  - Документы и видео из галереи — приходят как `DOCUMENT` (`.pdf`, `.mp4` и др.)
  - Видео, записанное в приложении, — приходит как `IMAGE` (`.webp`)
  - Геолокация — приходит как `LOCATION`; Bitrix24 не поддерживает геолокацию как отдельный тип, поэтому конвертируется в текстовое сообщение со ссылкой на Яндекс.Карты
- Входящее сообщение создаёт диалог в Открытых линиях Битрикс24 (или добавляется в существующий)
- **Содержимое, которое показать нельзя** (опрос, вложение без ссылки, неизвестный тип, пустой текст) — в диалог кладётся строка «⚠️ Клиент отправил вложение, которое невозможно отобразить. Попросите его написать текстом». Клиент ждёт ответа, поэтому факт обращения оператор должен видеть, даже если содержимое до нас не доехало. Пример: опрос в канале MAX приходит как `DOCUMENT`, а все поля внутри — `null`
- Если канал из вебхука не найден в БД — сообщение логируется и игнорируется
- Эндпоинт `/incoming` принимает методы **POST**, **GET** и **HEAD**: edna проверяет доступность URL двумя запросами (GET + HEAD) перед сохранением — оба должны вернуть 200 OK
- **Дедупликация:** edna может повторно отправить один и тот же webhook (retry). Каждое сообщение от edna имеет уникальный числовой идентификатор (`id`). Повторный webhook с тем же `id` распознаётся как дубль и игнорируется. Дублирование блокируется на трёх уровнях: проверка по таблице `messages` (уже доставлено), проверка по таблице `message_delivery_tasks` (уже в очереди) + уникальный индекс в БД для защиты при параллельных запросах

**Формат вебхук-запроса с входящим сообщением:**

Структура запроса описана в манифесте: [MAX Bot Incoming - LLM Manifest.md](MAX Bot Incoming - LLM Manifest.md)

#### 4.3. Отправка исходящих сообщений
- Оператор пишет ответ в Открытых линиях — сообщение передаётся на сервер MAX-бот через API
- Поддерживаются типы контента: **TEXT**, **IMAGE**, **VIDEO**, **AUDIO**, **DOCUMENT**
- При отправке файла (изображение, документ и т.д.) сервер определяет тип по MIME-типу и расширению файла, после чего передаёт файл в edna через прокси-эндпоинт `/file/{filename}?token=...&expires=...` — это необходимо, потому что edna требует URL с расширением файла в пути. URL подписан HMAC-SHA256 и действителен 10 минут; без валидного токена запрос возвращает 403. Файл хранится в памяти сервера 10 минут — этого достаточно, так как MAX Bot скачивает его за секунды и хранит на своём сервере
- Если сервер MAX-бот недоступен или вернул ошибку — оператору показывается ошибка в интерфейсе Открытых линий

**Формат API-запроса отправки сообщения:**

Структура запроса описана в манифесте: [MAX Bot send message - LLM Manifest.md](MAX Bot send message - LLM Manifest.md)

#### 4.3.1. Статус сообщения оператора («Просмотрено»)

Под сообщением оператора в Открытых линиях возможны **только два состояния**: «Просмотрено» или ничего. Разделить «доставлено» и «прочитано» нельзя — обработав статус *доставлено*, Битрикс тут же помечает сообщение *прочитанным*. Статусный метод коннектора существует ровно один — `imconnector.send.status.delivery`.

Поэтому правило такое: **метка ставится только по реальному прочтению.**

| Что сообщила edna | Что видит оператор |
|---|---|
| `SENT` — передано в MAX | ничего: клиент сообщение ещё не открывал |
| `READ` — клиент прочитал | «Просмотрено» |
| `UNDELIVERED`, `FAILED`, `CANCELLED`, `EXPIRED` | служебная строка «⚠️ Сообщение не доставлено…» (см. 4.3) |

Тип канала при этом не проверяется — реагируем на факт прочтения. В канале **MAX** `READ` приходит через несколько секунд после того, как клиент открыл сообщение. В **MAX Bot** его не бывает вовсе, поэтому метки там нет: сигнала о прочтении не существует, и любая метка была бы неправдой. Отсутствие метки в MAX Bot не пустое — при недоставке оператор получает служебную строку, значит её отсутствие означает «дошло».

Технически: edna присылает статус вебхуком на `/status/{webhook_token}` (адрес прописывается автоматически при подключении канала, как и адрес для входящих). Сообщение опознаётся по `requestId`, который равен `outMessageId` из ответа на отправку.

#### Соответствие параметров между API отправки и вебхуком входящих

Одни и те же сущности имеют разные имена полей в двух API:

| Сущность | API отправки (4.3) | Вебхук входящих (4.2) |
|---|---|---|
| Идентификатор канала | `sender` | `subject` |
| Идентификатор абонента в MAX | `maxId` | `subscriber.identifier` |

#### 4.3.2. Два типа канала: MAX Bot и MAX

Приложение поддерживает два типа канала edna. Тип определяется автоматически при подключении (из `/channel-profile`) и хранится в `channels.channel_type` — от пользователя ничего не требуется.

Входящие вебхуки у обоих типов почти одинаковы, а отправка различается:

| | MAX Bot | MAX |
|---|---|---|
| Эндпоинт | `/v1/out-messages/max-bot` | `/v1/out-messages/max` |
| Отправитель | `"sender": "<subject>"` | `"from": "<subject>"` |
| Получатель | `"maxId": "<id>"` | `"to": {"value": "<id>", "type": "MAX_ID"\|"PHONE"}` |

Перепутать их нельзя: на попытку отправить в канал MAX через эндпоинт MAX Bot edna отвечает ошибкой `default.subject.not_found`.

**Тип получателя** (`to.type`) берётся из массива `subscriber.identifiers` последнего входящего сообщения этого клиента **в этом же канале**; если ничего не сохранено — `MAX_ID`.

**Разделение диалогов («помеченный» chat.id).** Один и тот же человек имеет **одинаковый** идентификатор в MAX Bot и в MAX, а Битрикс при ответе оператора присылает только `chat.id`. Без дополнительной метки диалоги двух каналов слились бы в один, и ответ ушёл бы не в тот канал. Поэтому для всех типов канала, кроме MAX Bot, в Битрикс передаётся `chat.id` вида `{sender}:{identifier}`:

- в **Битрикс** уходит помеченный id — каждый канал получает свой диалог;
- в **edna** и в базу (`messages.subscriber_identifier`) идёт «голый» идентификатор;
- на исходящем метка разбирается по **последнему** двоеточию, канал ищется по `sender` — это переживает переподключение канала;
- **MAX Bot остаётся с голым id** — существующие диалоги не ломаются. Каналы без сохранённого типа тоже считаются MAX Bot.

Проверено на живом портале: Битрикс создаёт отдельный диалог на каждый `chat.id`, при этом **контакт и сделка в CRM остаются одни** — потому что `user.id` мы намеренно не помечаем.

**Имя клиента.** Канал MAX не передаёт `userInfo`. Если имени в вебхуке нет, оно берётся из прошлых входящих этого же клиента по любому каналу портала; не нашли — показывается идентификатор. Служебное сообщение `CONVERSATION_STARTED` («/start») в Битрикс не пересылается, но имя из него запоминается.

#### 4.3.1. Выбор открытой линии

- В настройках приложения отображается раздел **«Открытая линия Битрикс24»**
- Администратор выбирает открытую линию из выпадающего списка — список загружается из Битрикс24 в реальном времени
- После выбора: приложение активирует коннектор `max_bot` на выбранной линии и сохраняет её ID
- Если линия выбрана — отображается её название и кнопка «Изменить»
- Если линии в Битрикс24 есть, но ни одна не выбрана — показывается предупреждение с кнопкой «Выбрать линию»
- Если в Битрикс24 нет ни одной открытой линии — показывается кнопка **«Создать линию»**: приложение автоматически создаёт линию с названием «MAX Bot» через API Битрикс24 и активирует на ней коннектор
- Если линия не выбрана — входящие сообщения не маршрутизируются
- Администратор может изменить линию в любой момент через ту же форму
- **Не делаем:** автовыбор первой доступной линии при установке — опасно, может перезаписать настройки существующих интеграций на этой линии

#### 4.3.2. Установка приложения

- При установке Битрикс24 передаёт параметры авторизации: `AUTH_ID`, `REFRESH_ID`, `MEMBER_ID`, `DOMAIN`, `PROTOCOL`
- Приложение строит адрес REST API портала (`client_endpoint`) из параметров `DOMAIN` и `PROTOCOL`, если он не передан напрямую
- После сохранения данных портала — регистрирует коннектор `max_bot` и привязывает события (`OnImConnectorMessageAdd`, `OnImConnectorDialogStart`, `OnImConnectorDialogFinish`)
- Если регистрация коннектора или привязка событий упала при установке — это не блокирует установку, но устраняется автоматически при следующем открытии страницы настроек
- При открытии страницы настроек приложение автоматически: восстанавливает `client_endpoint` если он пустой, перерегистрирует коннектор и события — это обеспечивает корректную работу даже если что-то пошло не так при установке
- Страница настроек (`/settings`) принимает как GET-, так и POST-запросы: Битрикс24 открывает `PLACEMENT_HANDLER` через POST, браузерный переход — через GET
- URL обработчика событий формируется из переменной окружения `APP_BASE_URL` — она должна быть задана явно при деплое; если не задана, при старте сервера выводится ошибка в лог и события работать не будут
- Битрикс24 доставляет события (`OnImConnectorMessageAdd` и др.) на эндпоинт `/handler` в формате `application/x-www-form-urlencoded` с PHP-style вложенными ключами (например, `data[MESSAGES][0][chat][id]`), а не JSON. Обработчик парсит такой формат в нужную структуру. Если в теле запроса есть поле `event` — это событие Битрикс24, обрабатывается как событие. Если поля `event` нет — это открытие страницы через iframe, выполняется редирект на `/settings`

#### 4.4. Мультитенантность
- Одно приложение обслуживает множество порталов Битрикс24
- Каждый портал подключает и настраивает свои каналы независимо

#### 4.5. Хранение данных

Приложение должно хранить следующие данные (без ограничений по сроку и объёму). Конкретное решение для хранения выбирается на этапе разработки — возможно использование встроенных механизмов Битрикс24 или внешней БД:

- Информация о каждом портале Битрикс24, подключившем приложение
- Информация о каждом подключённом канале для каждого портала (включая дату/время подключения и отключения)
- Все сообщения с атрибутами:
  - Текст сообщения
  - Время отправки/получения
  - Направление (входящее в Битрикс / исходящее из Битрикс)
  - Контент (тип содержимого)
  - Другие атрибуты сообщения (идентификатор абонента, идентификатор диалога и т.д.)

#### 4.6. Логирование
- Логирование всех входящих и исходящих HTTP-запросов для отладки
- При обработке исходящего сообщения (ответ оператора → MAX Bot) логируется каждый шаг: полученные данные, причина пропуска если сообщение не обработано, факт отправки в edna и ответ edna
- При регистрации событий в Битрикс24 логируется URL обработчика, который передаётся Битрикс24
- При старте сервера логируется значение `APP_BASE_URL` — критически важная переменная для работы событий

#### 4.7. Производительность
- Пропускная способность: не менее 50 сообщений в секунду (входящие + исходящие суммарно)

## 5. Архитектура и безопасность

### SEC-1. Проверка подлинности входящих webhook

**Требование:** каждый входящий webhook от edna / MAX Bot должен проверяться на подлинность. Без проверки любой желающий может отправить поддельный запрос на `/incoming` и создать диалог в Битрикс24 от имени реального клиента.

**Реализация: токен в URL-пути (per-channel)**

При создании канала генерируется уникальный токен — 32 символа в hex-формате (UUID без дефисов, 128 бит энтропии). Webhook URL для каждого канала выглядит так:

```
https://edn-bit.onrender.com/incoming/6f4a8c2b1d3e4f5a...
```

При каждом входящем запросе сервер ищет канал по токену в URL. Если канал не найден — возвращает `403 Forbidden`, не раскрывая деталей. Попытка логируется.

GET и HEAD на тот же URL возвращают `200 OK` — это нужно, чтобы edna могла проверить доступность адреса перед сохранением.

**Почему токен в пути, а не параметр `?token=`:** токен в пути (`/incoming/6f4a8c2b...`) воспринимается как часть ресурса, не как явный параметр безопасности — меньше шансов случайно засветить его в логах или интерфейсе.

**Почему не HMAC-подпись:** точный формат заголовка подписи в edna не задокументирован. Токен в URL — индустриальный стандарт (используют Stripe, GitHub, Slack), не требует знания деталей стороннего API.

---

### SEC-2. Аутентификация событий от Битрикс24 и защита от replay-атак

**Требование:** события от Битрикс24 на `/handler` должны проверяться на подлинность. Без проверки злоумышленник может отправить поддельное событие и инициировать отправку сообщения от имени оператора, либо повторить перехваченный запрос.

**Реализация: проверка application_token + anti-replay fingerprint**

Каждое событие от Битрикс24 содержит поле `auth.application_token` — уникальный токен, выданный при установке приложения на портал. Сервер хранит этот токен и сверяет при каждом запросе: если токен отсутствует или не совпадает — запрос отклоняется.

Для защиты от replay-атак каждый запрос проверяется по SHA-256-отпечатку тела. Отпечаток сохраняется в таблице `seen_events`. Повторный запрос с тем же телом в течение 10 минут отклоняется. Старые записи удаляются при старте и периодически во время работы.

**Почему SHA-256 от тела, а не event_id:** Битрикс24 не гарантирует наличие уникального `event_id` в каждом событии. Хеш тела — универсальный и надёжный способ идентифицировать дублирующий запрос.

---

### SEC-3. Шифрование секретов в базе данных

**Требование:** при утечке дампа базы данных злоумышленник не должен получить доступ к секретам клиентов. Хранить `api_key`, `access_token`, `refresh_token` в открытом виде — недопустимо.

**Реализация: прозрачное шифрование через SQLAlchemy TypeDecorator**

Все три поля шифруются алгоритмом Fernet (AES-128-CBC + HMAC-SHA256) перед записью в БД и расшифровываются при чтении. Шифрование прозрачно для остального кода — роутеры и сервисы работают с обычными строками. Реализация сосредоточена в `app/crypto.py`.

Ключ шифрования хранится в переменной окружения `SECRET_KEY` (не в БД). Приложение не запустится, если `SECRET_KEY` не задан. Ключ скрыт из логов и диагностического вывода.

При первом запуске с включённым шифрованием блок миграции автоматически зашифрует все существующие открытые записи. Защита от race condition при параллельном запуске нескольких воркеров реализована через PostgreSQL advisory lock.

**Операционное ограничение:** `SECRET_KEY` неизменяем после первого запуска. Ротация ключа требует отдельной процедуры перешифровки всех записей в БД.

---

### SEC-4. Подпись URL файлов для edna

**Требование:** эндпоинт `/file/{filename}` не должен быть открытым — иначе любой может скачать кешированные файлы оператора.

**Реализация: HMAC-SHA256 + TTL 10 минут**

При добавлении файла в кеш генерируется URL вида `/file/{uuid}.ext?token=...&expires=...`. Токен — HMAC-SHA256 от пути и времени истечения, подписанный ключом из `SECRET_KEY`. Запросы без валидного токена или с истёкшим TTL возвращают `403 Forbidden`. TTL совпадает со временем жизни файла в памяти — 10 минут.

---

### SEC-6. Rate limiting входящих запросов

**Требование:** эндпоинты `/incoming` и `/handler` должны ограничивать количество входящих запросов. Без ограничений один источник может перегрузить сервис или исчерпать соединения к базе данных.

**Реализация: in-memory sliding window, 50 req/sec**

Модуль `app/services/rate_limiter.py` реализует sliding window без внешних зависимостей. Лимит: 50 запросов в скользящем окне 1 секунда. При превышении — `429 {"error": "too_many_requests"}`.

Ключи изоляции:
- `/incoming/{webhook_token}` — ключ `webhook_token` из URL, проверяется **до** обращения к базе данных
- `/handler` — ключ `member_id` из тела запроса, проверяется после парсинга тела

GET/HEAD на `/incoming` (пинги верификации edna) не ограничиваются.

**Почему in-memory, а не slowapi или Redis:** ключ для `/handler` находится внутри тела запроса — slowapi не может его прочитать в `key_func` без отдельного middleware, дублирующего логику парсинга. In-memory достаточно для single-instance деплоя на Render. При переходе к нескольким инстансам — потребуется Redis.

---

### SEC-11. Транспортная безопасность (HTTPS)

**Требование:** весь обмен данными между клиентами, Битрикс24, edna и сервером должен происходить исключительно по зашифрованному каналу. Передача webhook-токенов, API-ключей и токенов авторизации по незащищённому HTTP делает бессмысленными все остальные меры защиты: перехват одного запроса даёт злоумышленнику полный доступ к данным клиента.

**Реализация: HTTPS на уровне платформы + HSTS-заголовок**

HTTP → HTTPS редирект обеспечивается платформой Render — приложение HTTP-запросы не видит и не обрабатывает. Дополнительно каждый ответ сервера содержит заголовок:

```
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

Заголовок инструктирует браузер в течение одного года не допускать обращений к домену по HTTP, даже если пользователь явно введёт `http://` в адресную строку. Это устраняет риск downgrade-атак на клиентской стороне.

**Операционное требование:** при смене хостинга или деплое за собственным reverse proxy необходимо явно проверить, что HTTP-трафик не принимается приложением напрямую, а HTTPS-сертификат действителен и автоматически обновляется.

### Архитектурные решения реализации

| Решение | Суть |
|---|---|
| **AD-1:** `token.py` конвертирован в async вместе с `bitrix.py` | `refresh_token()` использует sync `httpx.post` → переведён в `async def` с `AsyncClient`, иначе обновление токена блокировало бы event loop |
| **AD-2:** Четыре обработчика в `api.py` → `async def` | Обработчики, вызывающие Bitrix-функции, стали `async def`; `disconnect_channel` оставлен как `def` — Bitrix-вызовов не делает |
| **AD-3:** Проверка на пустой текст в `handler.py` реструктурирована | Старая логика пропускала медиа-сообщения без текста до определения типа вложения; исправлено: пропуск только если нет ни текста, ни вложения |
| **AD-4:** Каждая media-функция открывает собственный `AsyncClient` | Функции остаются stateless — нет shared singleton, что упрощает тестирование |
| **AD-5:** Формат вложения Bitrix24 считается предположительным | Официальная документация не описывает поля файла; принято: `params.FILE.LINK/NAME/CONTENT_TYPE`. При несовпадении — логируем и пропускаем |
| **AD-6:** `settings_page.py` не изменялся | Не делает вызовов к сервисам Bitrix — вне скоупа async-рефакторинга |
| **AD-7:** Входящие файлы от MAX Bot — S3 URL передаётся напрямую в Bitrix24 | edna возвращает подписанный S3 URL с TTL ~1 год; Bitrix скачивает файл сам — промежуточное кеширование не нужно (в отличие от исходящих, где SIGN Bitrix истекает быстро) |
| **AD-8:** Очередь сообщений на PostgreSQL, без Celery/Redis | Приложение работает на Render single-instance (free tier). Таблица `message_delivery_tasks` заменяет брокер сообщений — не требует новой инфраструктуры. Revisit при переходе к нескольким инстансам |
| **AD-9:** HTTP handler возвращает 200 OK немедленно, доставка — асинхронно | Bitrix24 повторяет событие при не-200 ответе, создавая дубли. `/handler` всегда возвращает 200 и только кладёт задачу в очередь |
| **AD-10:** Файлы Bitrix скачиваются inline в handler, не в worker | SIGN-подпись в URL Bitrix24 истекает быстро. К моменту когда worker возьмёт задачу URL уже будет недействителен. `file_key` (UUID) в payload — стабильный ключ для реконструкции signed URL через `/file/{key}` |

## 6. Поведение в edge cases

| Ситуация | Поведение |
|---|---|
| Оператор закрыл диалог, абонент пишет снова | Поведение определяется стандартной логикой Открытых линий Битрикс24 |
| Сервер MAX-бот недоступен при отправке | Сообщение остаётся в очереди, worker автоматически повторяет до 6 раз (1с → 5с → 30с → 2м → 10м → 30м). После 6 неудачных попыток — статус `dead` в `message_delivery_tasks` |
| Несколько каналов MAX-бот на одном портале | Поддерживается, без ограничений на количество |
| Клиент удалил (деинсталлировал) приложение | Данные о каналах и сообщениях сохраняются в БД. Фиксируется дата/время отключения |
| Невалидный API-ключ | Проверяется при подключении: автонастройка webhook обращается к edna, при `401`/`403` канал не создаётся и пользователю показывается причина (см. 4.1) |
| Неверный Sender ID (нет канала с таким `subject` в edna) | Канал не создаётся; показывается ошибка с просьбой проверить совпадение Sender ID с названием подписи в edna |
| edna недоступна при подключении (сеть/прокси/5xx/cold start) | Канал создаётся, webhook нужно прописать в edna вручную по показанному URL (graceful fallback) |
| Входящий вебхук для неизвестного канала | Логируется и игнорируется |
| edna повторно отправила один и тот же webhook (retry) | Сообщение отправляется в Битрикс24 только один раз — повтор определяется по идентификатору сообщения и игнорируется |
| Хранение сообщений | Без ограничений по сроку и объёму |
