# Реализация #22: состояние и проверки

Обновлено 05.11.2026. Требования: [PRD 4.8](PRD.md#48-первое-сообщение-в-max-по-телефону-из-карточки-crm-22), порядок работ: [технический план](CRM_OUTREACH_TECH_PLAN.md).

Этот снимок описывает подготовку первой сборки с выключенной функцией. Подтверждение выкладки и реальных сообщений проводится отдельно; успешные локальные тесты его не заменяют. Перед выпуском тестовые сессии приведены к SessionLocal приложения (autoflush=False); повторно пройдены все 78 тестов и импорт app.main на отдельной пустой PostgreSQL без внешнего HTTP.

## Пользовательский процесс

Пользователь подключает канал через существующую веб-форму edna. Регистрация отправителя в CRM и синхронизация отключения/имени выполняются автоматически. Нового пользовательского этапа регистрации и отдельного переключателя CRM не будет. Для старых установок может потребоваться штатное подтверждение нового разрешения Битрикс24; технические действия с ключами и адресами регистрации не требуются.

Это зафиксированное требование. Отправка, реальные статусы, автоматическая синхронизация каналов, авторизация управления и диагностика uncertain реализованы локально. На сервере остаётся прежняя проба с искусственным статусом; новая версия туда не отправлялась.

## Основа, этап 1

Реализованы локально:

- модели `crm_message_providers`, `crm_outgoing_messages`, `crm_message_status_events`;
- внутреннее включение по порталу, по умолчанию false; глобальный переключатель по умолчанию false;
- nullable dedup_key очереди с уникальным индексом только непустых ключей; старые задачи остаются с NULL;
- добавочная миграция существующей БД и создание новой схемы; на PostgreSQL миграция сериализуется транзакционной advisory-блокировкой;
- явная диспетчеризация прежних task_type; неизвестный тип больше не исполняется как отправка в edna;
- явные CRM-типы отделены от прежних исходящих задач; отправка исполняется только при включении функции, статусы и удаление провайдеров — также при выключении;
- восстановление начатой CRM-отправки в uncertain без автоматического повторного POST; прежние типы сохраняют старую политику повтора;
- изолированный набор тестов, который не импортирует app.main, не читает проектный .env и запрещает настоящий HTTP; разрешены только явно заданные MockTransport и ASGITransport.

## Отправка и статусы, этап 2: локальная реализация

Реализованы:

- постоянный POST `/crm/messages/send`, JSON и фактическая PHP-форма Битрикс24, ограничение размера и вложенности;
- проверка сохранённого application_token, портала и привязанного CODE; секрет авторизации обязателен, отсутствие сохранённого токена не отменяет проверку;
- атомарная запись сообщения и задач одной транзакцией; HTTP 200 только после commit; недоступность БД возвращает 503;
- повтор callback с тем же CRM-message ID не создаёт вторую отправку, новый ID с тем же текстом означает новое сообщение; конфликт тела под старым ID отклоняется;
- телефон в международной форме, текст до 4000 символов, только тип канала MAX; MAX_BOT и неизвестные типы не подставляются в MAX;
- постоянный outMessageId сохраняется до HTTP; состояние `sending` и начало попытки фиксируются до передачи; переход сериализован с отключением канала блокировкой его строки;
- отправка `PHONE`/`TEXT` через существующий клиент edna, с необязательным outMessageId для сохранения старого формата остальных вызовов;
- отдельные задачи настоящих статусов, сохранение событий edna, защита от дублей/позднего SENT после READ; известный CRM-запрос принимает поздний статус даже после отключения канала;
- READ сохраняется отдельно и подтверждает delivered для CRM; самостоятельного статуса read в API Битрикс24 нет. HTTP-успех edna сам по себе не устанавливает sent или delivered;
- отдельные повторы статусного вызова, включая HTTP 200 с JSON-ошибкой, лимиты и ранний ERROR_MESSAGE_NOT_FOUND. Ошибка статуса не запускает повтор отправки сообщения;
- статусные HTTP-вызовы одного сообщения сериализуются PostgreSQL advisory-lock между экземплярами, независимо от commit при обновлении OAuth;
- новые пути логируют внутренние ID и безопасные коды ошибок, без auth, тела сообщения, телефона и сырых ответов с возможными секретами.

После ReadTimeout, потери соединения при передаче, HTTP 5xx/408/429 или непонятного успешного ответа результат — `uncertain`, без автоматического повторного POST. Только ConnectError/ConnectTimeout/PoolTimeout считаются отсутствием переданного запроса и допускают ограниченный повтор. Явный отказ HTTP 4xx, кроме 408/429, завершает отправку ошибкой. Реальный статус, пришедший раньше ответа HTTP, имеет приоритет. Сбой БД после успешного HTTP оставляет записанную начатую попытку: восстановление переводит её в uncertain, а не отправляет заново.

При глобальном выключении send-задачи не выбираются для отправки; локальная сверка отменяет ещё не начатые сообщения и планирует удаление отправителей. Уже сохранённые статусы продолжают передаваться в CRM. Переключатель портала также запрещает новые отправки. Это внутренние средства выпуска; пользовательских переключателей CRM не добавлено.

Этап 2 ещё не принят на стенде. Одних флагов недостаточно: нужен подтверждённый app_token, ожидаемый CODE приложения, действующий административный OAuth и messageservice. Ручные регистрационные URL не являются пользовательским процессом. Проба на сервере не менялась.

## Каналы, управление и диагностика, этап 3: локальная реализация

- При открытии настроек форма сама вызывает POST `/api/crm/prepare`. Сервер проверяет app.info (ожидаемый CODE и INSTALLED), user.admin и фактически выданный scope (`full=false`) через сохранённый endpoint портала. Затем отдельно проверяет сохранённый административный OAuth и наличие application_token. Только после успешных проверок включается портал и ставятся задачи всех активных MAX, включая старые каналы.
- UI передаёт текущий access_token из BX24.getAuth только заголовком Authorization. Токен сотрудника не записывается вместо административного. При включённой функции события прежнего `/handler` тоже не заменяют административный OAuth/endpoint; обновление выполняет существующий серверный refresh либо проверенная установка.
- Существующая форма POST `/api/channels` сохраняет канал, provider и задачу одной транзакцией. PATCH `/api/channels/{id}` меняет название без смены CODE. Отключение атомарно запрещает отправку, отменяет ещё не начатые сообщения с failed и ставит удаление provider. Переименование и отключение видны в той же таблице каналов; отдельной формы регистрации в CRM нет.
- Код отправителя стабилен: `edna_max_<channel.id>`. Существующий `edna_max_9` будет обновлён через sender.update, с постоянным HANDLER `/crm/messages/send`. `ERROR_SENDER_ALREADY_INSTALLED` требует update, а не ложного успеха. sender.list не возвращает HANDLER/NAME, поэтому они задаются update. Переименование/проверочная синхронизация уже работавшего provider не запрещают обычную отправку на время обновления NAME.
- Реестр возможностей в crm_channels.py включает только MAX (PHONE/TEXT); MAX_BOT, неизвестные и будущие типы выключены. У каждого поддерживаемого канала свой provider, имя и постоянный ID. Добавление другого типа потребует явной возможности и реализации отправки; автоматического попадания в MAX нет.
- Задачи sync_crm_provider имеют независимые повторы и desired/applied_revision. Внешние операции одного provider сериализуются advisory-lock. Изменение канала во время HTTP не теряется: применяется следующая версия. Открытие настроек администратором сверяет состояние заново, не плодит провайдеры; раз в 60 секунд worker проверяет локальное желаемое состояние. Ошибка сверки не блокирует прежние доставки Открытых линий.
- Управление каналами и запись настроек линии требуют подтверждённого администратора, когда функция включена либо уже использовалась этим порталом. Старые установки при выключенной функции сохраняют прежний процесс. Новый PATCH и диагностика всегда требуют администратора.
- Обновление известной установки проверяет новый AUTH_ID на сохранённом endpoint до принятия новых учётных данных; входящий URL не заменяет доверенный endpoint управляемого портала. После переустановки нужно автоматическое повторное подтверждение контекста/прав при открытии формы. Изменение домена самого портала требует отдельной проверенной процедуры, произвольный URL из браузера не принимается.
- При удалении приложения флаг сбрасывается, каналы отключаются, queued отменяются. Внешние методы с OAuth удалённого приложения не вызываются; что сама платформа удаляет из интерфейса, ещё проверить на стенде.
- В форме есть состояние синхронизации и список до 50 последних uncertain: название канала, время, CRM-message ID и outMessageId для сверки с поддержкой. Телефон, текст и секреты в диагностике отсутствуют. Кнопки слепого повтора нет.
- При включённой рабочей функции все маршруты пробы недоступны. При последующем глобальном выключении управляемый портал также не может вернуться к регистрации/искусственному delivered пробы. Промышленный выпуск всё равно должен иметь PROBE_22=0; сам временный модуль пока сохранён до подтверждения смены всех HANDLER.

Сценарии проверены локально, реальные ограничения интерфейса и позднего статуса после sender.delete остаются вопросами стендовой приёмки. Порядок: [CRM_OUTREACH_ACCEPTANCE.md](CRM_OUTREACH_ACCEPTANCE.md).

### Локальная проверка

Команда из корня Bitrix_edna:

```powershell
.\.venv\Scripts\python.exe -X utf8 tests/run_isolated.py
node tests/check_crm_ui.js
```

Проверки: основа/миграция и прежние обработчики; реальные формы callback; авторизация и конфликты ID; атомарность при отказе commit; отправка PHONE с постоянным ID; сетевые отказы и uncertain; сбой БД после передачи; ранние/повторные/поздние статусы; отсутствие регрессии READ; статусные повторы при выключенной отправке; поздний статус отключённого канала; прежний READ Открытой линии; формат реальных HTTP-запросов через заглушки.

Результат последнего полного запуска: 78 Python-тестов без пропусков, в том числе 11 на PostgreSQL 16; отдельно пройден Node-тест формы без браузера/зависимостей. PostgreSQL проверяет миграции, ограничения и callback, полный путь очереди с заглушками API, параллельную подготовку provider, отключение до захвата задачи и отключение во время HTTP. Node проверяет подготовку, исчезновение сообщения о синхронизации после успеха, передачу авторизации без refresh_token и переименование. Проверки настоящего портала/edna и визуальной работы формы этим запуском не заменяются.

Для PostgreSQL создан отдельный временный кластер в системном Temp, с новым портом и привязкой только к 127.0.0.1. Существующие БД/службы и DATABASE_URL приложения не использовались. После проверки процесс остановлен, каталог кластера удалён. При повторе без явно заданного тестового подключения 11 PostgreSQL-тестов будут пропущены; это не заменяет полный проверенный запуск.

PostgreSQL-тесты запускаются только с явно заданным `CRM_TEST_POSTGRES_URL` отдельной тестовой БД. Они создают и удаляют собственную случайную схему `test_crm_<uuid>`; DATABASE_URL приложения никогда не используется как запасной вариант. Не направлять их на промышленную БД.

## Состояние серверов и следующий шаг

- Код не коммитился и не отправлялся в GitHub; сборка Amvera не запускалась.
- Рабочая БД и настройки каналов не изменялись. Миграции выполнены только на временных локальных тестовых БД.
- PostgreSQL-проверки основы и отправки пройдены на отдельном локальном кластере. Для будущей выкладки нужно подтвердить резервное копирование целевого окружения. Для включения нужны открытые проверки этапа 0, автоматический жизненный цикл и приёмка реальной отправки.
- Автоматический жизненный цикл, управление и диагностика реализованы локально. Следующий этап — ограниченная приёмка на стенде по [готовому порядку](CRM_OUTREACH_ACCEPTANCE.md): подтвердить app_token и ожидаемый CODE, резервную копию, настройки выпуска; затем проверенная сборка и один тестовый получатель. Включение и выкладка в этой работе не выполнялись.
- Перед приёмкой нельзя обещать реальные доставки, правильное отображение нескольких каналов и поздние статусы удалённого provider на основании одних заглушек. Условные иконка/прочтение/история в Открытой линии остаются отдельными исследованиями этапа 4.
