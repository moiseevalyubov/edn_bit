# WHATSAPP_MESSENGER – реализация и проверка API

20.11.2026. База разработки – master, 8db97f4. Работа только локально; реальный API, commit, push и deploy не выполнялись. Telegram MVP принят владельцем на 8db97f4 / Amvera 11959d2, получение имени из CRM отложено.

## Согласованный объём

– Прежняя форма: название, API-ключ, Sender ID. Профиль находится через GET /api/channel-profile по точному subject, оттуда берутся subjectId и type=WHATSAPP_MESSENGER. Дополнительный Subject ID относится только к прежнему обходу Telegram.
– Отдельный коннектор edna_whatsapp_messenger на существующей общей Открытой линии; личный режим CHAT_GROUP=False. MAX/MAX Bot остаются на max_bot, Telegram – на edna_telegram.
– Входящий текст, ответ оператора по WHATSAPP_MESSENGER_ID, постоянная очередь, дедупликация, имена из userInfo/истории того же канала и переименование диалога при появлении имени.
– Если имени нет – участник подписан самим WhatsApp ID одной строкой, заголовок WhatsApp <ID>. Это техническая подпись, не полученное CRM-имя. Отдельного получения данных CRM нет.
– Собственные user.id и chat.id: wa:<32 hex SHA256(sender)>:<WHATSAPP_MESSENGER_ID>. Sender включён также в user.id, поскольку личный режим группирует по нему. Переименование и переподключение с тем же Sender сохраняют ID.
– Статусы коррелируются по каналу и requestId=outMessageId. Только READ вызывает «Просмотрено» в Открытой линии; SENT/DELIVERED его не имитируют. Поздние статусы принимаются и после отключения.
– Вложения пока не отправляются; входящий неподдерживаемый контент даёт видимое предупреждение с доступной подписью. Исходящее вложение получает уведомление оператору, без скачивания URL и потери секрета SIGN в очереди.
– Первое сообщение из сделки по PHONE, медиа и автоматическое объединение контактов не входят в этот этап. Низкоуровневый контракт PHONE есть в PDF, CRM-провайдер нового канала не регистрируется.
– Новые таблицы, колонки и разрешения не добавлены. Новые типы задач используют существующую очередь. Старая версия worker их не понимает – при откате сначала оценить и остановить новые операции, не возвращать старый образ вслепую.

## Подтверждённые входы

– Владелец подтвердил: обнаружение канала как у MAX/MAX Bot; версия и форма URL отправки как у Telegram; тип WHATSAPP_MESSENGER; READ поддерживается. Реального примера входящего пока нет, разрешено писать код по аналогии с Telegram с явными пометками.
– docs/whatsapp_beta.pdf, страницы 1–3: from, to.value, to.type=PHONE/WHATSAPP_MESSENGER_ID, outMessageId, content; ответы phone/whatsappMessengerId; статусы requestId, subject, subjectId, status, statusAt, error. В PDF URL оставлен как api/v{№}/out-messages/{channel}, входящий webhook не приведён.
– Bitrix MCP: проверены параметры imconnector.register, imconnector.activate, imconnector.send.messages, imconnector.send.status.delivery и imconnector.chat.name.set. MCP даёт справочник, а не подтверждение прав и поведения живого портала.

## Следующая живая приёмка

1. Подключить тестовый Sender без ручного Subject ID; проверить оба callback, личный коннектор и общую линию.
2. Входящий текст → правильный диалог/штатный CRM-трекер → ответ оператора → устройство. Отдельно проверить отсутствие имени/телефона и повтор обращения после закрытия.
3. Получить реальный READ и увидеть «Просмотрено»; SENT/DELIVERED не должны рисовать прочтение. Проверить UNDELIVERED, ранние/повторные статусы и поздний READ после отключения.
4. Два WhatsApp-отправителя и одинаковый клиент – ответ только через выбранного отправителя. Переподключение сохраняет маршрут старого диалога.
5. Сверить весь реестр WA-A01..A06. Настоящие ключи, телефоны, имена и секретные webhook URL в fixtures/публичные документы не сохранять.
6. Регрессия MAX, MAX Bot, CRM MAX и Telegram на предпроде. Новые scopes и прод не менять.
